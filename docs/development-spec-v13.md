1. 現行ソース・公開版・保存形式・依存ライブラリを調査し、すべての要求を「実装済み／部分実装／未実装／要調査／仕様判断待ち」に分類する。動作未検証で完了扱いしない。
2. 既存の正常機能、艦艇設計・艦隊編成・セーブを壊さず、必要ならマイグレーションを設ける。旧データを読み込むときは欠けた項目を安全な既定値で補う。
3. **実装の所有者は機能ごとに一つ**。下記の「旧ID→統合実装」表により重複を排除する。IDは消さず、受入条件・参照先・進捗として残す。

6. サンドボックスでは自由設計・自由編成を優先する。予算、政治、勢力、技術解禁等のキャンペーン固有制約は任意で適用する場合を除き強制しない。

8. 100隻超の艦隊戦を基準に負荷を計測する。全艦の全設備を高頻度で逐一計算する設計にしない。
9. **表中の84件は履歴を持つ要求IDの数**。完全に独立した84個のモジュールを作る意味ではない。複数IDが同じ機能を検証する場合は、実装を統合し進捗を同時に紐づける。
10. 作業終了時は変更ファイル、ID別状態、検証結果、互換性、残存問題、次の作業を明確に報告する。

## 2. 実装の共通アーキテクチャ（唯一の処理系）

### 2.1 オブジェクト/設計データ

艦艇・航空機・ウォーカー・車両・固定ステーションを共通の設計コンポーネントと幾何構造に載せる。ただし移動物理・操作体系・補給/搭載ルールまで同一にはしない。必要なデータの概念例：

```ts
// 擬似型。既存ソースの構造を確認し、移行方法と互換性を設計してから導入。
type Platform = 'ship'|'aircraft'|'vehicle'|'walker'|'station';
type LinkKind = 'power'|'heat'|'structural'|'control';
type Design = { id:string; version:number; platform:Platform;
  hull:HullGeometry; parts:PartInstance[]; groups:EditGroup[]; links:SystemLink[];
  installedAssemblies?:AssemblyInstance[] };
type PartInstance = { id:string; definitionId:string; localTransform:Transform;
  damageState?:DamageState; settings?:Record<string,unknown> };
type EditGroup = { id:string; members:(PartId|GroupId)[]; transform?:Transform };
type SystemLink = { id:string; kind:LinkKind; fromPort:string; toPort:string;
  capacity?:number; health?:number; autoGenerated?:boolean };
type AssemblyTemplate = { id:string; version:number; origin:Transform;
  children:PartInstance[]; groups:EditGroup[]; internalLinks:SystemLink[];
  externalPorts:PortDefinition[]; metadata:Metadata };
type FormationTemplate = { id:string; version:number; name:string;
  slots:FormationSlot[] };
type TaskForce = { id:string; factionId:string; shipAssignments:ShipSlotAssignment[];
  formationId:string; anchor:Transform; velocity:Vector3;
  maneuverOrder?:ManeuverOrder; aiDoctrine?:Doctrine };
type BattleScenario = { version:number; factions:FactionDeployment[];
  victoryConditions:Condition[]; randomSeed?:number };
```

- テンプレート（パーツ・陣形）／配置インスタンス／戦闘時の実体は別。名前ではなく安定IDで参照する。
- 参照先IDの存在、循環参照、ネスト上限、破損セーブの検査を共通化する。複製・ミラー時は部品IDと内部リンク参照先を一貫して再採番する。
- インポート時の単位系、スケール、座標系、ローカル姿勢を明示し、旧版データ移行で不明な値を黙って変形しない。
- 設計形状の物理量は**重複領域を二重計上しない**。船体内部に食い込んだ外装・重なる構造材・格納区画の容積関係を処理する際は、質量・体積・可用容積を別々に定義する。既存計算ルールを調査したうえで互換修正。

### 2.2 共通編集基盤

単一の選択セット（PC Shift、スマホ複数選択トグル、コントローラーの追加選択コマンド）、Undo/Redo、プレビュー、スナップ、頂点・面・部品の対象種別切替、XYZ移動・回転・鏡像・寸法考慮等間隔配置、グループ階層、入力数値欄を共有する。個別エディター（艦体/切削/陣形/複合パーツ）が保持するのは**対象データ型・検査ルール・表示**のみとする。

グループ操作は設計内だけで完結。**パーツ登録**はテンプレート保存、**陣形保存**は配置スロットを持つテンプレート保存、**切削形状保存**はCSG用の形状プリセット保存であり、保存先と機能的意味を混同しない。

### 2.3 電力・熱・センサーの一方向パイプライン

```text
リアクター / 蓄電池 / 発電設備
    ↓ [power] 給電経路・容量・保護装置
武装充電 / 推進 / シールド / センサー / 生活設備 / その他
    ↓ 部品効率・負荷から廃熱発生（有効出力と外部放出エネルギーは除外）
各設備の局所熱ストレージ
    ↓ [heat] 熱輸送経路・容量・遮断・損傷
内蔵散逸 / 外装散逸 / 翼内散逸 / 通常放熱
    ↓ 実際に散逸したエネルギーと散逸方式
EM・赤外・ニュートリノ等の帯域別放射シグネチャ
    ↓ 敵センサーの帯域対応・距離・雑音・統合判断
探知段階 / 表示輝点 / 追跡 / 射撃解
```

同じ出力を同時に「発電量」「排熱量」「放射量」として重複加算しない。給電と熱輸送は**別ネットワーク**だが同じリンクグラフ実装を共有してよい。装置の排熱“容量”ではなく、その時点の**実処理量**が放射を決定する。

### 2.4 艦隊編成・陣形・シナリオ

艦艇の設計とコストは設計側が提供し、任務群は**艦艇ID→陣形スロット**の関係を保存する。陣形テンプレートは艦艇設計に依存せず、サイズ・役割・優先順位を持つ配置スロット群。戦闘シナリオは任務群と初期配置・勢力・勝利条件を参照する。自軍と敵軍のエディターは同一で、キャンペーン専用制約は設定フラグで適用する。

### 2.5 更新頻度・信頼性

- ゲームループの時刻・単位を統一。艦艇運動／射撃・AI戦術・電力熱管理・センサーを必要に応じ別周期で更新し、差分がないデータは再計算しない。更新周期の数値は計測で決定。
- 高価なメッシュ生成・切削は必要なら非同期/ワーカー等へオフロードし、作業中の入力をキューイング。**編集要求が消失しない**こと。完了順序・キャンセル・Undoを定義する。
- セーブとローカルテンプレートの入出力はバージョン・マイグレーション・検証・バックアップ方針を持つ。

### PLAN-024 — 新造艦の予算要求・政治情勢によるランダム査定・設計改定

**目的：** 設計した新造艦の費用を共和国政府に要求し、戦果や戦前／戦時の政治情勢に応じて満額・一部削減・大幅削減のいずれかが抽選で承認される。減額時は承認枠内に収まるまで再設計が必要。

**要求事項：**

- 序章のパルパティーン議長による特別予算は固定のチュートリアルイベントとして区別する。

## 6. 任務群の協調運動・オリジナル陣形（AI-001、FORM-001〜010）

### 6.1 基準運動と速度

- 任務群は基準位置、隊形角度、速度ベクトル、希望速度、陣形ID、艦艇スロットを持つ。各艦の目標座標は基準点＋回転したローカルスロット座標から算出する。
- 持続航行の速度は原則、**最も遅い所属艦艇の持続可能速度以下**。加速能力、推進機関損傷、電力制限、機動方向と耐久、艦艇配置を反映する。
- 陣形旋回時は外側艦の必要速度・回転半径・スロット追従能力を評価し、隊形維持を選択した場合は全体を減速する。艦艇は瞬間移動させない。
- **船首方向（attitude/heading）、移動ベクトル、任務群の隊形座標系を別状態**にし、船首の一斉回転だけを「陣形が転換した」と誤判定しない。

### 6.2 旋回/再編方式

| 命令 | 動作・陣形を変える条件 |
|---|---|
| 陣形維持旋回 | 相対配置を可能な限り保って基準方向を変更。必要なら減速 |
| 順次旋回 | 先行艦の航跡を後続艦が順にたどる。単縦陣に好適 |
| 一斉回頭 | 各艦が同時に船首を回す。位置関係自体を必ずしも変えない |
| 陣形転換旋回 | 目的地と同時に別のスロット配置へ再編。無理な軌道交差は回避 |
| 最短時間優先 | 陣形の一時的な乱れを許し、可能な範囲で早く進路変更 |
| 安全優先 | 艦艇サイズや接近状態を考慮し、間隔を広げて転換 |

初期陣形：単縦、単横、斜行、梯形、楔形、円形・防御、自作。**斜行陣は方向によって再配置距離を小さくできる**が、常に瞬間転換可能とせず、各艦の姿勢変更・加減速は必要。具体の転換時間は各艦の到達距離・加速度・旋回能力・衝突回避から推定し、最遅艦の制約も反映する。スロット再割当は最短距離だけでなく艦種・旗艦役割を固定する。

### 6.3 陣形エディター

三次元X/Y/Zのスロット編集、ドラッグと数値入力、複数選択・等間隔・対称・回転・スケール・複製、保存・再読込・JSON入出力。各スロットは役割（旗艦、主力、護衛、防空、空母、補給等）、優先艦種/サイズ、位置、基準方向、優先度を持つ。テンプレートは船名や設計図に固定しない。艦艇を割り当てる際に安全距離を計算し、重複を警告。PC/タッチ/ゲームパッドで操作する。

### 6.4 戦闘中AI

任務群AIは戦術的目的、交戦距離、速度、隊形、進路、陣形転換を決定し、個艦AIはスロット追従、射撃、緊急回避、局所障害物回避、損傷離脱を担当。艦艇が個別に敵へ突撃して乱戦化する挙動を抑える。陣形切替にはクールダウンと再評価閾値を設ける。衝突回避/緊急回避/明示的個艦命令を隊形維持より優先する。大規模戦時は任務群単位で経路計画を共有する。

## 7. サンドボックス艦隊編成・再現可能な戦闘（PLAN-002/003、SBOX-001〜004、BAL-001）

## 8. 船体・切削・3D構造・機能付き主翼（PLAN-010/013、EDIT-001〜004、WING-001〜004）

### 8.1 形状エディターを一本化

基本形状の自由変形は、球など曲面形状を除いて共通多面体エディターで実施。X/Y/Zの頂点移動、複数頂点選択/同時移動、面移動・押し出し・傾斜、鏡像編集、頂点追加・削除、スナップ、数値入力、Undo/Redoを共有する。切削用形状は直方体、三角柱、台形柱、円柱、楕円柱、円錐、円錐台、球、楕円体、カプセル、トーラス、ユーザー定義多面体。切削形状の保存と再利用が可能。

繰返しブーリアンでの面消失・裏返り・非多様体・ゼロ面積面・法線不良・極薄壁・交線問題・衝突形状との不一致を修正する。船体を削ったときトレンチが勝手に切削面へ貼り付かないようにし、トレンチ施工範囲と非施工部の高さ連続性を維持する。切削の積み重ねを含めてセーブ互換とパフォーマンスを検証。外部3Dデータは**編集可能な構造形状への変換**として取り込み、機能付きパーツへの自動変換はしない。

### 8.2 形状・容積・質量

構造物が船体へめり込む場合、内部に隠れる外装部分を二重計上しない。重複構造体は幾何学的な合成と質量計算を適切に扱う。内部区画の規定容積を維持しつつ、外装・近傍区画との干渉に応じて収まる形状への自動調整を許す（形状破綻・必要容積不足時は警告）。構造体に設定された外形と、独立の物理設備の体積・質量・可用内部容積を混同しない。

### 8.3 主翼とSフォイル

構造だけの翼状パーツは維持し、**容積と設備配置能力を持つ機能付き主翼**を追加する。既存多面体エディターで形状編集。主翼内部には散逸装置・通常放熱・エネルギー伝達・補強・可動機構を配置可能。**散逸装置のない翼に自動的な高エネルギー散逸ボーナスは付与しない。** 翼の展開/遮蔽/機構損傷は搭載設備の最大能力を変えるが、同じ負荷なら実散逸量は必ずしも変わらない。

Sフォイル機構は回転軸、収納/展開角、展開時間・速度、質量・耐久、可動部と艦体/装備との干渉を持つ。小型機にも大型艦にも適用可能、翼なし艦は内蔵散逸で成立する。設計時に可動範囲の干渉検査を行い、戦闘中の状態が性能・放射シグネチャへ反映する。

## 9. ユーザー定義の複合パーツ（USERPART-001〜006、UI-007と区別）

設計中に外装＋エンジン＋動力炉＋給電設備などを複数選択し、**再利用可能な複合パーツとして明示的に登録**できる。名前・カテゴリ・説明・アイコン/プレビュー・基準点・取付方向・内部接続ポートを保存し、通常パーツと同じカタログへ登録。検索・複製・改名・削除・JSON入出力。**グループ化するだけでは自動登録しない。**

カタログから配置した後は移動/回転/コピー/削除/グループ化/左右・上下（必要なら前後）対称設置できる。子パーツのローカル座標、回転、ノズル方向、ポリゴン巻順、接続ポートを鏡映時に正しく変換。対称化による質量・推力・発電・廃熱・容積を実体に応じ計算し、架空の一律性能ボーナスも二重計上も禁止。外装が船体に重なる部分の容積は8.2に従う。

テンプレート定義と配置インスタンスを分離し、**初期は配置時の独立コピー方式**を推奨。子IDとリンクを再採番。設置先で外部接続できないと点検警告、接続もないのに無限給電・推進可能としない。配置後に全体選択/子部品編集/分解が可能。テンプレート削除後でも既存の配置済み実体はセーブから復元できる。必要なら後からリンク更新方式を追加する。

**スケール変更の扱い：** 機能設備（炉、機関、砲等）を無条件に拡縮して性能増減させない。外装・構造など形状スケール可能な子要素と、設備仕様が固定の子要素を区別し、互換性違反は警告。複合パーツ全体を任意倍率で伸縮できることを必須要件と誤解しない。

## 10. 艦全体の統合電力・熱管理・破損（ENG-001〜007、PLAN-005/006/014〜017）

### 10.1 変更の核心

**武装専用の独立した排熱計算を廃止し、武装・推進・主動力炉・シールド・電子装置・生活設備・ハイパーウェポンを、同じ艦内の電力供給＋熱輸送＋エネルギー散逸ネットワークに接続する。**

内蔵型・外装型・翼内型の高エネルギー散逸装置と通常放熱装置は、このネットワークの接続先として表す。武装に専用の散逸装置を設置する設計は可能だが、それも共通ネットワーク上で**専用経路として接続された装置**にすぎない。複数武装での散逸共有、複数設備からの負荷分担、経路の冗長化を認める。

### 10.2 収支計算・熱輸送

- **発電出力≠廃熱量**。設備の有効使用電力、ビーム・弾体・排気などの外部へ出るエネルギー、蓄電・蓄熱、損失を区別する。
- 艦艇の集計値：発電可能上限、現在出力、蓄電量、設備ごとの電力要求/供給、廃熱生成、熱輸送容量、最大散逸能力、実散逸量、局所/総蓄積熱、許容熱容量、出力制限、故障状態。
- **熱源→輸送→散逸**の経路ごとに処理能力を判定。例：主砲の廃熱100、共用散逸装置の処理能力200でも、間の熱輸送路が60なら**主砲側の余剰40は局所蓄熱**へ回る。散逸装置の総容量を足し算しただけで解決しない。
- 給電と熱輸送は共通のリンク基盤で管理しても、**別の容量・故障・接続グラフ**を持つ。初期は周辺配置に基づく自動接続、後に専用経路と手動接続を選べるようにする。パーツの内部ポートと複合パーツの外部ポートの整合も検査。
- 武装威力・砲身・連装数・加速器・充電装置から消費電力・充電速度・損失を計算し、リアクター出力不足と廃熱処理不足の**両方**が連続射撃を制限する。エンジン設計/シールド/センサー負荷も同じルールを使う。
- 熱容量が残れば一時的な高出力・低放射運転を許す。飽和すると出力抑制・緊急停止・過熱損傷へ進む。遮断・停止には応答時間を与え、壊れた経路へ無限に排熱できない。

### 10.3 散逸パーツの役割

| 装置 | 役割 | 共通の扱い |
|---|---|---|
| 内蔵型高エネルギー散逸装置（ENG-003） | 船体内部に配置、内部容積・質量・接続が必要 | 散逸能力・負荷・稼働量・損傷を持つ |
| 外装型高エネルギー散逸装置（ENG-004） | 外装・主翼外面などに配置、被弾弱点になり得る | 同じネットワークの出力装置 |
| 通常放熱装置（ENG-005） | 低出力・通常温度帯の電子/生活等の負荷 | 同じ枠組みの別の熱負荷種別、万能の高エネルギー散逸とはしない |
| 送電・分配・遮断設備（ENG-006） | 電力ネットワークの経路と保護 | 熱輸送路とは別系統 |
| 熱輸送・分配・遮断設備（PLAN-014、ENG-006内の熱種別） | 発生熱を専用/共用散逸へ運ぶ | 経路容量・接続・損傷・安全弁 |

数値モデルの単位（W/J 等）、装置効率、最大温度、熱容量、各エネルギーの変換係数は定量仕様未決定。作業時に既存のパラメータを保護し、**次元の整合を取って仮定を明示**する。高エネルギー散逸/ニュートリノ放出はスター・ウォーズの**架空技術モデル**であり、現実で実証された冷却方法と表現しない。

### 10.4 散逸設備の被弾と重大故障

1. 散逸装置または輸送経路が損傷し、接続が変化する。
2. 生き残った経路へ負荷を再分配し、その経路の**実効処理能力**を更新する。
3. 処理不能な熱は関連装置や区画の局所蓄熱となる。条件に応じ自動出力制限・非常遮断・停止が作動する。
4. 対応する通常兵装系統の重大過熱が閾値を超えれば、**武装用電力区画を破壊**する。
5. 発電機直結ハイパーウェポン系統で重大過熱/過負荷となり遮断が間に合わなければ、**直結したジェネレーターが爆発**する。周辺区画へ損傷が伝播する。ジェネレーターではなくハイパーウェポン本体が爆発するという仕様にしない。
6. 冗長化・低出力化・安全停止が成功すれば即時爆発に至らない場合もある。**損傷先を決める旧仕様は維持し、発生条件を統合熱管理で詳細化**する。

### 10.5 設計診断と戦闘HUD

点検で「熱源」「給電経路」「熱輸送経路」「散逸設備」「余裕率」「断線」「過負荷」「装置ごとの残熱」「低放射持続時間」の概要を示す。通常航行/戦闘/最大出力の負荷プリセットで診断。透視モードで熱・給電ネットワークを表示するが、通常描画では不要な内部設備を常時描画しない。故障時はどの部品の機能が制限されるか追跡可能にする。

## 11. 放射シグネチャ・センサー・Sフォイルの連動（SENS-001〜005、WING-004）

- 散逸装置は種類と実散逸量に応じ、仮想的なニュートリノ・赤外・電磁シグネチャを持つ。推進機関の放射や能動センサーの放射は独立項目。**ニュートリノを通常レーダーで探知する設定にはしない**。HUD上の「輝点」は複数帯域のセンサー融合結果である。
- 実放射強度は最大散逸能力に比例して固定的に発生させない。リアクター出力増大・主砲充電・急加速等が廃熱を増やした**結果**として実散逸と放射が増える。
- Xウイング型のSフォイルを開くことで、搭載装置の最大散逸能力/遮蔽が変わり、高出力で連続戦闘しやすくなる。**展開それ自体は必ずしもニュートリノ放射を増やさない**。翼のない大型艦や主翼を持つ大型艦も同じルール。
- 探知段階：未探知→微弱反応→放射源検知→概略位置推定→追跡→識別→射撃に必要な精密捕捉。ユーザーに見せる段階数はUI簡素化可。放射検出だけで艦種/精密位置を確定しない。
- 通常／低放射／高出力／緊急散逸モードを持つ。低放射では出力制限・一時蓄熱が可能で、蓄熱限界超過なら隠密運転を続けられない。負荷がなければSフォイル展開中も低放射にできる。
- 初期は等方放射と距離・感度・雑音による簡略検出モデルでよい。方向性、星雲、遮蔽、観測時間は後段階の拡張。ゲーム内シグネチャの強度と射撃精度を区別する。
- 100隻超の戦闘時、すべての帯域×全艦ペアを毎フレーム総当たり計算しない。探知候補の空間分割、遠方は低頻度、イベント駆動、前回結果のキャッシュを利用する。

## 12. PC・スマホ両用ゲームパッド（PAD-001〜005）

## 15. 検収テスト（実装済み扱いの必要条件）

### 15.1 基本編集・保存

- Shift追加/解除、スマホ複数選択、ゲームパッド追加選択で**同じ選択状態**になる。グループ化してもテンプレート登録は行われず、明示的登録のみカタログへ追加される。
- X/Y/Zの複数移動、個別/全体回転、実寸法考慮の等間隔配置、左右上下ミラー、Undo/Redoをテスト。左一覧と3Dビューが一致し点検結果が常時表示。
- 旧版の設計/セーブを読み、再保存・再読み込みしてパーツ位置・接続・質量・グループ・艦艇特性が保たれる。
- 外装＋エンジン＋動力炉＋電力・熱接続をユーザー定義パーツとして保存し、別艦へ配置・左右対称配置・独立編集・再読込。推力/発電/質量/廃熱が**二基分のみ**計上されること。欠損した外部接続は警告。

### 15.2 船体・切削・取り込み

- 球/楕円体/円柱/自由多面体で切削を繰り返し、面欠落・法線反転・メッシュ破綻・トレンチの誤複製がない。保存後も形状・干渉・容積一致。
- 外部3D形状を取り込んだ場合、モデル外観だけでなく頂点・面が編集可能である。設備機能を自動生成せず、プレイヤー操作で後から付加できる。

### 15.3 任務群・AI・艦隊シナリオ

- 異なる最大速度と損傷を持つ艦を編成し、最遅艦に合わせて持続航行する。旋回中は各艦の位置・速度・衝突を検証し、不自然な瞬間移動なし。
- 単縦/単横/斜行で同じ進路変更を行い、方向ごとに**スロット移動距離と必要時間**が異なることを確認する。艦首の向きだけ変える命令と隊形再編命令を区別する。
- オリジナル3D陣形を保存し、別の任務群/異なるサイズの艦に適用。任務群/陣形テンプレート/シナリオが別々に保存できる。
- 自作艦を敵側へ配備し同型艦同士を戦わせる。固定シード・同じ両軍編成で戦闘を再現可能。AIが不必要に近接乱戦しない。

### 15.4 統合熱管理・被弾とセンサー

- リアクター→送電→主砲充電→廃熱→熱輸送→共用散逸へ実際に処理が伝わる。主砲廃熱100・散逸容量200・熱輸送60なら40が局所蓄熱する（例示用正規化値）。
- 同じ散逸装置へ複数熱源を接続し合計容量を超えれば熱蓄積・出力制限が発生。専用/共用設備の動作結果が同じアルゴリズムで算出される。
- 散逸装置を損傷→経路を再評価→熱負荷を再分配。安全停止した場合は**必ずしも爆発しない**。停止しない通常武装の重大過熱は武装用電力区画を破壊。直結ハイパーウェポンの重大過負荷は**接続ジェネレーターが爆発**。
- Sフォイル展開により最大散逸能力が変化。発熱量・実散逸量を一定に保持できる状態では、展開だけでニュートリノ放射が必ず増えるわけではない。
- 放射強度とセンサー感度・距離によって接触段階が変わり、微弱反応から即時精密追跡や艦種特定へ飛ばない。

### 15.5 ゲームパッド・日英UI・性能

- ALG-MOGPADSCNのOS接続→Webブラウザ認識→ゲーム内入力を個別に検証（iOS、可能ならAndroid/PC）。Gamepad API未認識時の診断を表示し、非対応と接続失敗を混同しない。
- キーボード、マウス、タッチ、ゲームパッドを交互に使用して設計/陣形/戦闘/メニューに不具合がない。デッドゾーン、長押し、切断/再接続を検証。
- 英語切替で設計、艦隊編成、戦闘、マップ、キャンペーン、ユーザー定義パーツ、センサー、ゲームパッド設定の**固定日本語が残らない**。TF/CTF軍事用語の対応を確認。
- 100隻超の同一シナリオで描画/AI/衝突/熱/センサーの負荷を個別記録。機能追加前後で比較。画面操作不能やシミュレーションの停止が起こる場合は完了扱いしない。

### 15.6 キャンペーン・予算・マップ

- 24 BBY序盤12段階を順番に進行し、4対4模擬戦、基地補給、特別改修、地上演習、ミュニファスント級拿捕、新造艦設計、予算査定と再設計、設備・ステーション/3D構造体設計を体験する。
- 予算減額後は承認額を超える設計で建造不可。設計変更ごとに承認額を再抽選しない。議長特別予算と通常査定を区別。ルーサン制限は予算とは独立。
- 主要航路では複数星系を途中停止なしに通過でき、支線では星系ごとに必ず停止。銀河図と作戦図は航路グラフ/星系IDが一致する。
