# 実給電ベースの推進モデル

現在は[リアクター出力を基準とする機関入力](reactor-powered-propulsion.md)、[推力と抵抗が釣り合う最高速度](force-balanced-sublight-speed.md)、実出力スロットルを使う。以下は過去の実装・検証の記録であり、手入力の機関定格・密度超過の変換ペナルティ・固定最高速度・無抵抗の惰性航行は現在の方式へ置き換わる。実給電、電力収支、実推力・実廃熱の共通計算と、既存の物理的制約は継続して使用する。

追記：給電線の詳細モデルは廃止し、現在は[電源点と距離による数値計算](numerical-electrical-distribution.md)を使う。以下に記録した従来の配線の体積・質量・描画は、過去の実装と検証結果を示す。機関からノズルへの動力伝達路は直線の実体として扱う。

推力の正本をノズル容積から、共通配電で機関が実際に受け取った入力Wへ変更した。内蔵型はノズルと機関本体を独立して保持し、外装型は接する本体とノズルを一体で扱う。設計プレビュー、艦隊AI、直接操縦、艦載小型機、平時・編隊移動で共通の入力・推力計算を使う。

## 現行基準と計算入口

実装前の作業基準は `dd9ef12`。指定監査コミット `2736808388b51bcdbfd4cb01aa71e7e79ff14deb` を取得し、20関数を比較した。`nozzleThrust`、`nozzleDemand`、基準表、機関経路、配電、熱、稼働率、速度式の19関数は本文が一致した。`fleetProfile` の差は既存の兼用砲プロファイル追加で、監査対象の旧推進式は同じだった。ハッシュは [propulsion-audit-baseline.json](benchmarks/propulsion-audit-baseline.json) に記録した。

入口は `js/core.js` の以下の関数。

| 入口 | 責務 |
|---|---|
| `resolveEngineSpec` / `updateEngineSpec` | 検証済み定格・固定係数・有限密度・実機関形状・費用 |
| `engineTransmission` / `engineDriveRoutes` | 反応炉から本体への配電路と、本体からノズルへの動力伝達路の実寸・容量・接続 |
| `getEngineInputLimit` / `buildPropulsionRequests` | 熱・局所損傷・接続・幹線・操縦要求から受入要求Wを作る |
| `allocateConnectedPower` / `allocateShipPower` | 推進・兵装・シールド・生活設備・冷却の共通収支。共有炉・共有幹線を一度だけ使用 |
| `resolvePropulsion` / `solveShipPropulsion` | 実入力WからN、5%廃熱W、力ベクトル、物理加速度を計算 |
| `propulsionProfile` / `propulsionPreview` | 設計の接続・形状をコンパイルし、同じソルバーで運転条件をプレビュー |
| `propulsionMotion` | 構造・慣性制約後の現在加速度を、既存運動と戦闘倍率へ一度だけ接続 |
| `migrateLegacyPropulsion` | 旧部品基準の定格・係数・形状を冪等に移行し、互換冷却を無効化 |

`P_request = min(u × R, B, R × h × d)`、`F = P_actual / C`、`Q = .05 × P_actual`。質量は既存集計のトンを境界で一度だけkgに変換する。廃熱を理由に推力へさらに `.95` を掛けない。旧4.5倍の機関要求、要求充足率による熱制限相殺、6%待機推力、`p.accel` と実給電による二重減衰を撤去した。

固定検証は `R=1e18 W`、`C=2e9 W/N`、`M=1e6 kg`、構造・慣性制約なしで行う。

| 条件 | 実入力W | 実推力N | 推進廃熱W | 無制限加速度m/s² |
|---|---:|---:|---:|---:|
| 全要求・健全・十分な供給 | `1e18` | `5e8` | `5e16` | `500` |
| 熱受入上限25% | `2.5e17` | `1.25e8` | `1.25e16` | `125` |
| 熱停止 | `0` | `0` | `0` | `0` |
| 要求ゼロ | `0` | `0` | `0` | `0` |
| 供給50% | `5e17` | `2.5e8` | `2.5e16` | `250` |

物理加速度は `min(実力ベクトルの大きさ / 質量kg, 構造上限) × 慣性支持率` とし、慣性支持率を現在の実力へ一度だけ掛ける。定格時だけの上限に置き換えて部分出力で制約を回避しない。戦闘側では既存 `FLEET_RULES.accelScale=.002` を一度だけ掛ける。計画最大加速度、現在の実加速度、MGLTによるゲーム上の速度上限を区別する。ノズルの奥行きによる速度係数は中立化した。停電・熱停止・ゼロ要求時は既存速度を保持し、新規加速・無償制動・旋回加速を与えない。

## 採用した暫定係数

すべてゲーム用係数であり、公式設定・現実技術の確定値ではない。

| 項目 | 値 |
|---|---:|
| 新規標準 `C` | `2.0e9 W/N` |
| 旧内蔵タービン移行 `C` | `2.330706322054385e9 W/N` |
| 旧露出タービン移行 `C` | `5.41461208407102e9 W/N` |
| 推進廃熱 | 実推進入力の `5%` |
| 炉廃熱 | 実発電負荷の `4%`。既存係数を維持 |
| 標準／高密度／超高密度の入力密度上限 | `3.4e17 / 3.4e18 / 3.4e19 W/m³` |
| 上記の費用倍率 | `1 / 1.8 / 3.5` |
| 移行専用の有限密度上限 | `3.4e24 W/m³`。改修警告付き、自由な新規選択・定格増強は禁止 |
| 価格の基準密度／基準電力 | `3.4e17 W/m³ / 1e18 W` |
| 定格費用／密度超過費用係数 | `2 / 20`（既存価格単位） |
| 絶対入力上限 | `1e32 W` |

追加機関費用は `gradeMultiplier × [2 × R / 1e18 + 20 × V × max(0, R / (3.4e17 × V) − 1)²]`。既存のノズル・機関本体・導路の設置費用へ加算し、内部機関の容積や導路を二重計上しない。同じ容積で定格を上げれば価格が増え、密度上限を超す編集は部品を変更せず拒否する。移行用W/N係数を通常の自由編集値にはしない。

## 保存移行と熱の順序

旧機関の単体 `F0/P0` を読み、`ratedInputW=P0`、対応する固定移行プロファイルを設定する。`machineryLengthM`、`machineryRadiusM`、`machineryOffsetM`、給電・熱ノード、共有機関参照を保存する。内蔵機関は実部品 `engineCore` の直径と長さから円筒容積を導出する。外装一体型の実作動部は既定のフラスタムを使い、明示的な `machineryShape:'cylinder'` も保持できる。円筒は `πR²L`、既定形状は実フラスタムの容積・質量・容量を計上し、形状の違いを保存・複製後も保持する。自己申告容積や炉までの導路の長さは受入容量に使わない。

エンジンの外装カバーとベルの付け根は表示用の原モデルとして保持し、実作動部の寸法・定格・所有者から独立させる。実作動部を小さくしても外装全体を縮めず、内蔵機関へ接続したノズルも原モデルの付け根を省略しない。実作動部の容積・質量・有限容量と給電・廃熱は別に計算し、外装カバーを第二の実機関として数えない。表示モデルの外接体積を機関の受入容量には使わない。

経路は「反応炉 → 配電 → 実機関本体 → 動力伝達 → ノズル」の順になる。内蔵型の機関本体は独立した実部品で、一つの本体から複数の独立したノズルへ接続できる。外装型は機関本体とノズルが一体になる。ISDは主機3基を主反応炉のすぐ後ろ、補機4基を補助炉付近の独立した本体で受け持ち、計7基をそれぞれのノズルへ接続する。CR90はノズルごとに一つの内蔵本体を機関ブロックの首付近へ置く。他の作例の汎用・内蔵ノズルも、反応炉からの距離がノズル径の4倍と反応炉径の2倍の大きい方を超える場合は、個別の近傍本体を使う。既存の外装機関と航空機は、各本体とノズルが一体の独立した機関を保つ。

反応炉から機関本体までの配電路は、長さに応じて損失と発熱を生む。同じ経路の送電量は「本体への受電量 ＋ 配電損失熱」に分かれ、機関の5%廃熱は本体が実際に受け取った電力から求める。配電の損失熱を機関の変換熱として再加算しない。共有する上流回路は一度だけ設置し、その総電力を機関と他の下流負荷で分け合う。

配電効率は実経路長 `L` mに対する `η = exp(-1e-5 × L)` とする。1 kmで約1%の損失になるゲーム上の仮定である。受電要求 `P` Wを満たすには上流から `P / η` Wを送り、その差を配電管の独立した高エネルギー熱源へ積算する。多段経路では各段の送電・受電・損失を保存し、配電管の局所過熱はその管の実伝達容量を制限する。配電管の熱輸送路は実際の管と設置済みの高エネルギー散逸装置から再構築し、各装置の実容量で分配する。生成管の一時的な部品IDに依存した熱配線は図面へ固定しない。

本体の受電量の5%は機関の変換熱、95%は軸出力になる。ノズルの推力係数は `.95 × 2e9 W/N` とし、本体受電を基準とする既存の `2e9 W/N` の推力則を保つ。機関本体から各ノズルへの伝達路には追加損失を設けず、有限の軸動力容量と実寸を与える。各ノズルの伝達路が切断・破壊・閉塞すれば、そのノズルへの供給を止める。同じ本体から複数の出口を使っても、機関の入力や定格推力を出口数だけ複製しない。

配電路と動力伝達路は、機関本体と別の占有物として実寸の容積・質量・価格を計算する。導路を延ばしても機関本体の受入容量は増えない。部品移動、回路容量、接続、船体形状の編集時に物理経路を再計算し、保存図面の実部品と接続からも再構築する。

別の構造部材の間にある小さな継ぎ目は、有限長の実配管を追加して接続する。配電管の両端の断面がそれぞれ別の実部材内へ完全に収まる場合に限り、追加部分の容積・質量・費用と配電損失を計上する。大きな空隙を無配管で渡したり、一つの船体内の隔壁を外へ迂回するために継ぎ目用の配管を流用したりしない。

旧図面で汎用・内蔵ノズルが別ノズルの機関を参照していた場合は、元の機関形状・位置・定格・接続炉を互換リゾルバーで維持する。新しい内蔵機関は独立した `engineCore` を所有者とし、ノズルを削除しても機関本体を削除しない。外装一体型を内蔵機関の共有出口として指定する接続は無効にする。外装型の本体とノズルの間に隙間がある配置も無効とし、標準の接続位置でノズル長を変える場合は接点を保つよう本体の位置を合わせる。

`propulsionMigration.previous` に移行前部品の公開保存データを保持する。`propulsionModelVersion=1` により再移行を止め、旧性能倍率は復活させない。保存、共有JSON、ローカル設計、複合パーツ、艦載設計、左右・上下ミラー、複製、Undo/Redoに新フィールドを通す。

艦載設計の図面がある場合、保存済みの性能キャッシュより実部品・実配電路・損傷対象を優先する。キャッシュの配線で配電損失を省いたり、機関やノズルを重複して出力を増やしたりできない。加速度の質量も実図面を下回らせず、元のキャッシュがさらに重ければその質量を保持する。ノズルだけを複合パーツとして取り出した場合は、元の機関への接続を未接続として保持し、暗黙の機関本体を新造しない。

熱計算は旧保存を含めて厳格運転に統一する。旧機関の `legacyCoolingInputW` は読み込み・移行時に0へ正規化し、互換冷却や不可視の散逸能力を作らない。接続された実物の散逸装置と有限容量の熱輸送路を使い、その装置自身の給電も必要になる。再読み込みで定格・冷却能力・部品を積み増さない。

更新順は「前回の機関ごとの熱制限 → 今回の共通配電 → 実入力の5%を各機関へ積算 → 熱ネットワーク更新」。同じ機関を複数出口で共有しても入力・推力を複製しない。局所蓄熱・損傷・停止は機関ごとに保つ。実冷却には接続先ごとの電力予約を使い、別の無給電冷却器の容量を平均で融通しない。散逸量は今回の流入と蓄熱の合計を超えず、大きい時間刻みはサブステップ化する。

冷却用の電力予約も送電と受電を区別する。未使用の予約から配電損失熱や炉熱を作らず、実際に冷却へ使った受電量に対応する送電量・損失を計上する。同じ配電管を兵装と共有していても、兵装の即時消費と冷却の実使用を重複させない。

炉の4%廃熱は配電台帳の実出力を炉ごとに積算する。別系統の炉へ平均で熱を移したり、停止した炉へ推進負荷を加えたりしない。冷却の電力と炉廃熱も同じ実供給から計上する。共有ノズルの推進廃熱は所有する機関の熱ノードへ一度だけ入れる。

設計画面の「持続運転能力」は **未判定（熱平衡未解決）** と明示する。定格や冷間瞬間出力を持続能力と呼ばない。航続表示の炉25%固定負荷は参考条件として区別し、未実装のリアルタイム燃料消費を実装済みと表示しない。

## 最新mainとの接続・検証の範囲

実装コミット `b866f4b` の後、作業ブランチへ最新main `36c18a9` の戦略AI・補給船・移乗攻撃を取り込んだ。4設計の比較は取り込み前に固定したVMの記録であり、最終統合後のブラウザ・CPU測定とは区別する。取り込みによる新しいLH-3210は艦艇であり、12機種の艦載機価格カタログへ追加する対象ではない。

PR作成直前にmainへ入った `042a398` の地上戦も取り込んだ。英語辞書で隣接した追加項目の競合は、推進・地上戦の両方を保持して解決した。推進ソルバー、質量、艦載機プロファイル、艦の移動処理には追加変更がなく、艦隊更新から地上戦へ時計を渡す処理と共存する。地上車両は独立した走行規則を使うが、共有の費用集計と格納・揚陸経路は追加の地上戦テストで確認する。最終のブラウザ・CPU記録はこの取り込み後のソースに対応する。

旧集計プロファイルしかない艦は、既存の有限な機関需要W、実際の機関モジュール、独立した質量tから読み取り専用の互換プロファイルを作る。既存の有限な `p.accel` は `legacyUpperMovementCapMps2` という移動上限としてだけ保持し、推力・定格・質量の計算には使わない。構造・慣性・旧給電の内訳を回復できない保守的な上限であり、正確な再編集には設計図が必要。基準電力・機関・質量がない場合は推力を補わない。

移乗攻撃で艦が牽引へ抵抗する力も、今回実際に配分された力ベクトルから求める。旧加速度と稼働率を再乗算しない。抵抗する機関の要求も共通配電に含め、牽引装置の系統停止・局所遮断では対象位置を動かす前にロックを解く。衝突、既存の重力・喪失艦の落下、牽引、ハイパードライブ遷移の外力・拘束処理は、推進器の無償出力とは区別している。
