# 実給電ベースの推進モデル

推力の正本をノズル容積から、共通配電で機関が実際に受け取った入力Wへ変更した。ノズル、内部機関、受入定格を独立して保持し、設計プレビュー、艦隊AI、直接操縦、艦載小型機、平時・編隊移動で共通の入力・推力計算を使う。

## 現行基準と計算入口

実装前の作業基準は `dd9ef12`。指定監査コミット `2736808388b51bcdbfd4cb01aa71e7e79ff14deb` を取得し、20関数を比較した。`nozzleThrust`、`nozzleDemand`、基準表、機関経路、配電、熱、稼働率、速度式の19関数は本文が一致した。`fleetProfile` の差は既存の兼用砲プロファイル追加で、監査対象の旧推進式は同じだった。ハッシュは [propulsion-audit-baseline.json](benchmarks/propulsion-audit-baseline.json) に記録した。

入口は `js/core.js` の以下の関数。

| 入口 | 責務 |
|---|---|
| `resolveEngineSpec` / `updateEngineSpec` | 検証済み定格・固定係数・有限密度・実機関形状・費用 |
| `getEngineInputLimit` / `buildPropulsionRequests` | 熱・局所損傷・接続・幹線・操縦要求から受入要求Wを作る |
| `allocateConnectedPower` / `allocateShipPower` | 推進・兵装・シールド・生活設備・冷却の共通収支。共有炉・共有幹線を一度だけ使用 |
| `resolvePropulsion` / `solveShipPropulsion` | 実入力WからN、5%廃熱W、力ベクトル、物理加速度を計算 |
| `propulsionProfile` / `propulsionPreview` | 設計の接続・形状をコンパイルし、同じソルバーで運転条件をプレビュー |
| `propulsionMotion` | 構造・慣性制約後の現在加速度を、既存運動と戦闘倍率へ一度だけ接続 |
| `migrateLegacyPropulsion` | 旧部品基準の定格・係数・形状・互換冷却を冪等に移行 |

`P_request = min(u × R, B, R × h × d)`、`F = P_actual / C`、`Q = .05 × P_actual`。質量は既存集計のトンを境界で一度だけkgに変換する。廃熱を理由に推力へさらに `.95` を掛けない。旧4.5倍の機関要求、要求充足率による熱制限相殺、6%待機推力、`p.accel` と実給電による二重減衰を撤去した。

固定検証は `R=1e18 W`、`C=2e9 W/N`、`M=1e6 kg`、構造・慣性制約なしで行う。

| 条件 | 実入力W | 実推力N | 推進廃熱W | 無制限加速度m/s² |
|---|---:|---:|---:|---:|
| 全要求・健全・十分な供給 | `1e18` | `5e8` | `5e16` | `500` |
| 熱受入上限25% | `2.5e17` | `1.25e8` | `1.25e16` | `125` |
| 熱停止 | `0` | `0` | `0` | `0` |
| 要求ゼロ | `0` | `0` | `0` | `0` |
| 供給50% | `5e17` | `2.5e8` | `2.5e16` | `250` |

物理加速度は `min(実力ベクトルの大きさ / 質量kg, 構造上限) × 慣性支持率` とし、慣性支持率を現在の実力へ一度だけ掛ける。定格時だけの上限に置き換えて部分出力で制約を回避しない。戦闘側では既存 `FLEET_RULES.accelScale=.002` を一度だけ掛ける。計画最大加速度、現在の実加速度、MGLTによるゲーム上の速度上限を区別する。ノズルの奥行きによる速度係数は中立化した。停電・熱停止・ゼロ要求時は既存速度を保持し、新規加速・無償制動・旋回加速を与えない。

## 採用した暫定係数

すべてゲーム用係数であり、公式設定・現実技術の確定値ではない。

| 項目 | 値 |
|---|---:|
| 新規標準 `C` | `2.0e9 W/N` |
| 旧内蔵タービン移行 `C` | `2.330706322054385e9 W/N` |
| 旧露出タービン移行 `C` | `5.41461208407102e9 W/N` |
| 推進廃熱 | 実推進入力の `5%` |
| 炉廃熱 | 実発電負荷の `4%`。既存係数を維持 |
| 標準／高密度／超高密度の入力密度上限 | `3.4e17 / 3.4e18 / 3.4e19 W/m³` |
| 上記の費用倍率 | `1 / 1.8 / 3.5` |
| 移行専用の有限密度上限 | `3.4e24 W/m³`。改修警告付き、自由な新規選択・定格増強は禁止 |
| 価格の基準密度／基準電力 | `3.4e17 W/m³ / 1e18 W` |
| 定格費用／密度超過費用係数 | `2 / 20`（既存価格単位） |
| 絶対入力上限 | `1e32 W` |

追加機関費用は `gradeMultiplier × [2 × R / 1e18 + 20 × V × max(0, R / (3.4e17 × V) − 1)²]`。既存のノズル・機関本体・導路の設置費用へ加算し、内部機関の容積や導路を二重計上しない。同じ容積で定格を上げれば価格が増え、密度上限を超す編集は部品を変更せず拒否する。移行用W/N係数を通常の自由編集値にはしない。

## 保存移行と熱の順序

旧機関の単体 `F0/P0` を読み、`ratedInputW=P0`、対応する固定移行プロファイルを設定する。`machineryLengthM`、`machineryRadiusM`、`machineryOffsetM`、給電・熱ノード、共有機関参照を保存する。内部機関の容積は実寸の機関フラスタムから導出し、自己申告容積や炉までの導路の長さは受入容量に使わない。

`propulsionMigration.previous` に移行前部品の公開保存データを保持する。`propulsionModelVersion=1` により再移行を止め、旧性能倍率は復活させない。保存、共有JSON、ローカル設計、複合パーツ、艦載設計、左右・上下ミラー、複製、Undo/Redoに新フィールドを通す。

旧機関には移行時の `legacyCoolingInputW` を固定して持たせ、互換冷却をこの値から求める。新規・定格増強分には不可視の冷却を足さず、実設備が必要になる。再読み込みで定格・互換冷却・部品を積み増さない。

更新順は「前回の機関ごとの熱制限 → 今回の共通配電 → 実入力の5%を各機関へ積算 → 熱ネットワーク更新」。同じ機関を複数出口で共有しても入力・推力を複製しない。局所蓄熱・損傷・停止は機関ごとに保つ。実冷却には接続先ごとの電力予約を使い、別の無給電冷却器の容量を平均で融通しない。散逸量は今回の流入と蓄熱の合計を超えず、大きい時間刻みはサブステップ化する。

炉の4%廃熱は配電台帳の実出力を炉ごとに積算する。別系統の炉へ平均で熱を移したり、停止した炉へ推進負荷を加えたりしない。冷却の電力と炉廃熱も同じ実供給から計上する。共有ノズルの推進廃熱は所有する機関の熱ノードへ一度だけ入れる。

設計画面の「持続運転能力」は **未判定（熱平衡未解決）** と明示する。定格や冷間瞬間出力を持続能力と呼ばない。航続表示の炉25%固定負荷は参考条件として区別し、未実装のリアルタイム燃料消費を実装済みと表示しない。

テストファイルは `tests/propulsion-*.cjs`。最終ソースで専用の **96テストが成功**した（4.26秒）。内訳はコピー3、編集UI13、形状8、モデル12、移動18、配電・熱16、熱源11、表面給電8、直接操縦7。ブラウザは [propulsion-browser.json](benchmarks/propulsion-browser.json) と日英・PC/スマホのPNG、性能は [propulsion-110.json](benchmarks/propulsion-110.json) を参照。実Chromiumで4条件の表示、フォーム変更、Undo/Redo、実入力・N・5%廃熱、WebGLコンテキストを確認した。日本語PCのケースでは機関の共有・専用切替をネイティブ選択欄で操作し、専用へ戻した際の定格・形状・係数を確認した。物理スマホ、実ゲームパッド、長時間の戦闘映像、GPUのFPSは測定していない。

最終CPU測定は110隻の独立した運転状態を、0.25秒刻みで20回（5秒分）更新した。110隻分の配電・推進・熱更新は中央値 **8.721ms**、95パーセンタイル **13.915ms**。内訳の中央値は配電＋推進7.347ms、熱更新0.688msで、別計測した110回分の純推力解決は0.402msだった。設計・プロファイルの初期構築は1.661秒。実行中の `enginePaths`、`surfacePatches`、`resolveEngineSpec`、`machineryGeometry`、`fleetModules` はすべて0回で、毎更新の形状・全経路再構築を行っていない。CPUは非専有で、ブラウザ確認などの処理も同時に動く検証環境での値である。

艦載機の価格カタログは価格モデル11で再生成し、同じ設計計算から作った `powerProfile` も含める。初回出撃時に設計図の全統計・熱経路を作り直さず、検証済みカタログのプロファイルを利用できる。生成スクリプトの `--output` は指定ファイルに生成ブロックだけを書き、並行編集される `js/core.js` 全体を書き戻さない。

## 比較・再実行

汎用機関、ISD内蔵型、ヴェネター露出型、Xウイングの形状・質量・価格・単体基準・配電別W/N・加速度・廃熱・冷却・速度を [propulsion-comparison.json](benchmarks/propulsion-comparison.json) に記録する。物理的な変化、旧バグ修正、価格係数、ノズル深さに由来した速度補正の撤去を区別する。

同じ旧設計を直接複製して推進移行した結果は以下。価格は艦体の建造価格で、小型機カタログの搭乗員費を含む総価格とは区別する。

| 設計 | 質量t 旧→新 | 価格 旧→新 | 価格比 |
|---|---:|---:|---:|
| 汎用 | `653285.621908 → 同値` | `2361178 → 2361485` | `1.000130` |
| ISD内蔵 | `37627330.964271 → 37627332.657207` | `190091994 → 244521033` | `1.286330` |
| ヴェネター露出 | `6864581.122917 → 同値` | `37489032 → 590734997` | `15.757542` |
| Xウイング | `23.588423 → 同値` | `177922 → 188341` | `1.058559` |

**ヴェネターの約15.76倍は、採用した暫定密度費用式による大きな価格変更**である。移行前の推力へ質量を合わせる補正ではない。船体・装甲・炉の密度係数は変更していない。

単体定格の合計 `P0/F0` は4設計とも浮動小数点誤差内で維持した。冷間・健全・全要求・射撃要求なしのランタイムでは、4つの配電モードそれぞれで実入力を解き、以下の推力を得た。これは熱平衡後の持続能力ではない。

|---|---:|---:|---:|
| 汎用 | `1.538124e20 / 7.690619e10` | `25.475192 → 25.475192` | `74.711871 → 76.752720` |

| ヴェネター露出 | `1.080000e24 / 1.994603e14` | `17792.390840 → 17792.390840` | `1202.639191 → 1201.220805` |

旧基準は `dd9ef12` の不変チェックアウトまたは `git archive` の展開先を用意し、`node scripts/capture-legacy-propulsion.cjs LEGACY_SOURCE_DIRECTORY /tmp/ks-propulsion-baseline-dd9.json` で再作成できる。現行コードにこの旧基準キャプチャを実行しない。

ブラウザスクリプトの再実行にはPlaywrightとChromiumが必要。今回の検証は環境に既存のPlaywrightと `/usr/bin/chromium` を使った。

ベンチマークはCPU上の共通配電・推力・熱更新を測り、110種類の設計生成、衝突、GPUや描画FPS、長時間のメモリ増加を測るものではない。元の保存形式でロードした際の既存正規化による形状差を混ぜないため、代表比較は旧設計の同じ公開データを複製し、推進移行だけを適用する。
