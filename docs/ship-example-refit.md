# 作例艦の機関・配電・排熱設備

選択可能な艦船27作例を、現在の推進・電力・熱モデルに合わせて組み直す。新しい作例の構築時に改装し、保存済みのプレイヤー設計は保存された装置と配線から計算する。武装の種類と配置は [指定4艦](named-example-armament.md) と [艦種別の系列](example-weapon-families.md) を参照。

## 機関と実際の加速

機関は標準の入力係数 `2e9 W/N` と通常の有限な機関密度を使う。内蔵型は機関本体を独立した実部品として置き、そこから複数のノズルへ伝達路を接続できる。外装型は機関本体とノズルが一体になる。機関本体に必要容積を確保し、旧式機関向けの大きな密度上限や互換冷却を使用しない。

ISD、ヴェネター、アクラメイター、エグゼクターの目標加速は既存の参照表を使用し、最終的な実質量から必要推力を求める。実際に収まる機関区画の容量を上限とし、目標に届かない場合も到達可能な加速をそのまま使用する。それ以外は各作例の既存部品の定格推力を引き継ぐため、追加設備の質量も実加速に反映される。戦闘プレビューの機関要求は35%なので、計画最大加速とは別の値になる。

カタログの見出しと基本仕様は最大性能を表示する。加速は機関定格と構造・慣性の上限、砲撃は搭載砲の全一斉射、シールドは全蓄積容量を使う。現在の配電、充電、熱や損傷による実運転値は運転状況の欄へ分け、基本仕様のために実際の電力配分や加速を変更しない。

## 反応炉と配電

マンデイターIIは [指定性能](mandator-ii-refit.md) の7.70×10²⁶ Wへ実反応炉の容積を調整する。他の作例は既存反応炉の実容積・出力を維持する。推進・砲・シールドの同時最大出力に合わせた発電量の増強は行わない。砲撃やシールドへ多く配電すれば、機関が受け取る実電力と推力は低下する。慣性補償、構造維持、反応物供給設備を実区画として搭載し、有限の発電量を現在の計算モデルで使用できるようにする。レキューザント大型型では球状砲の機構と干渉した補助炉2基を、同じ実容積の船内区画へ収め直す。再構成したメッシュの容積比較にはFloat32座標の誤差として相対 `1e-7` を許容し、発電量はその実測容積から求める。

各反応炉から機関本体へ、実物の有限容量の配電路を接続する。武装、シールド、冷却設備などには配電・蓄電区画を経由する配線を設ける。兵装の配電路は、発電設備と冷却・生活負荷を踏まえた設計容量を持つ。連射時の再充電は、この容量と運転時の配電量で制限される。

局所機関の本体は、ノズルに対して吸入口側にある実反応炉のうち最も近い炉を優先して給電する。該当する炉がなければ全炉から最も近いものを選び、不足分は他の近傍炉から有限容量で分担する。機関本体の位置と既存の発電量を保ち、実配電路の距離に応じた損失と発熱を計算する。

推進系統は「反応炉 → 配電路 → 機関本体 → 伝達路 → ノズル」の順につながる。反応炉から機関本体までは電力の配電路、機関本体から各ノズルまでは推進用の伝達路として扱う。ISDの主機3基は主反応炉のすぐ後ろにそれぞれ別の本体を置く。補機4基も補助炉付近の個別の本体で受け持ち、計7基を一つずつ対応するノズルへ接続する。CR90は11基のノズルに対応する11基の内蔵本体を機関ブロックの首付近へ置く。他の汎用・内蔵ノズルも、炉から離れたものは個別の近傍本体を使う。既存の外装機関と航空機は、各本体とノズルが一体の独立した機関を保持する。

配電路が長いほど損失と発熱が増える。反応炉の実送電量を機関本体の実受電量と配電損失熱へ分け、その受電量から実推力と機関自身の発熱を求める。受電量の5%は機関の熱、95%はノズルへ送る軸動力になる。共有する幹線は一度だけ設置し、その有限容量を下流の機関や他の負荷で分け合う。複数のノズルが同じ機関本体を使っても、本体の入力と推力を複製しない。

配電路とノズルへの伝達路は、容量に応じた実断面を持ち、他の固定設備を避ける。径・長さに応じた容積、質量、価格を計上し、伝達路の容積を機関本体の受入容量へ加えることはない。切断・破壊・閉塞した枝線はその先への供給を止める。保存図面には実部品と有限容量の接続を保存し、読込時に同じ物理経路を再構築する。

超兵器は元の給電炉を保持し、充電の予約電力も既存の発電量から差し引く。通常の艦載砲と同様に、超兵器の充電熱にも実物の輸送路を設ける。

## 排熱

熱関係の互換運転は全設計で廃止し、旧保存や面設定のない設計も厳格運転で計算する。内蔵冷却の仮想能力と超兵器への散逸能力の自動割当は使用しない。作例には通常の内蔵型高エネルギー散逸区画と有限容量の熱輸送路を搭載する。区画の容量と質量は船内に確保した実容積から求める。既存反応炉の発電量と配電条件で実際に動かせる負荷に合わせて容量を決める。冷却設備の消費電力、炉で発生する変換熱、機関・砲・シールドの損失熱、生活・電子設備と冷却設備自身の廃熱を収支へ含める。

船内区画の自動配置では、互いに接する隔壁を容積の重複と誤判定して装置を停止させないよう、パッキング済みの区画同士は実際の直方体群で判定する。実際の容積の重なりは引き続き検出する。

## MC30c

MC30cは指定の500 GT球状単装砲16基、球状3連装PD10基、魚雷・爆弾発射機8基、トラクター2基を搭載する。GR-75のレーザーターレットは2基とし、過大な武装を搭載しない。MC80の添付図に基づく各100基の配置と、指定4艦の武装基数は保持する。

## CR90とスフィルナ級

CR90は添付STLを基に全長150 mで作り直し、標準作例には500 MT連装軽ターボレーザー2基と6 MT単装重レーザー4基を搭載する。500 MT軽ターボレーザーの単装・連装・4連装はカタログで選択できる。11基のノズルにはそれぞれ独立した内蔵機関を接続する。

旧ハンマーヘッドの作例キー `hammerhead` を維持し、表示名を「スフィルナ級コルベット」に変更する。添付STLを全長116.7 mへ合わせ、艦首の左右に6 MT連装重レーザーを各1基、後部に500 MT連装軽ターボレーザーを1基搭載する。

元STLの識別、座標変換、砲座とノズルの扱いは [CR90のモデル](cr90-stl-model.md) と [スフィルナ級のモデル](sphyrna-stl-refit.md) に記録する。

新しい砲の出力は1門ごとに500 MT＝`0.0005 TT`、6 MT＝`0.000006 TT`。一斉射はこの値に門数を掛ける。MC30cなどの既存500 GT砲（1門`0.5 TT`）とは別の装備として保持する。

## 1発ごとの砲出力

専用ポイント防御砲は1門1発100 kt（`1e-7 TT`）、航空機レーザーは1門1発2 kt（`2e-9 TT`）に統一する。固定レーザーと重レーザーは各1門、小型旋回砲塔は実モデルに合わせて2門として数える。500 MT軽ターボレーザーと6 MT重レーザーには、それぞれ指定された出力を使う。

砲の出力値はすべて1発あたりであり、連装砲の一斉射は「1門1発の出力×門数」、平均出力は「一斉射のエネルギー÷射撃間隔」で求める。射撃間隔を短くしても1発の出力を薄めず、電力とレーザーガスは完全な1発分を確保してから発射する。

小隊の集計射撃も、レーザーとイオン砲の合計を実際に兵装へ届いた電力で制限する。保存された射撃間隔を短くしても、同じ受電量から余分な射撃エネルギーを作らない。標準航空機の射界はカタログに前計算して保持し、最初の射撃で作例全体を同期構築しない。

航空機用イオン砲 `cion` はカタログと標準作例から廃止する。旧保存の砲、表面砲列、複合パーツ、艦載設計に残る参照も読み込み時に除去し、以前の集計火力から復活させない。艦船用の175 TT、40 TT、150 TTなどのイオン砲は保持する。

## カタログと計測

艦隊カタログはモデル16で編集可能な作例から生成する。機関設計の前計算は共通の面装備ビューを一度だけ取得し、砲ごとに全船体をハッシュし直す処理を避ける。物理値が同一であることと、呼び出し回数の低減を回帰テストで検証する。生成時と同じ船体・統計・プロファイルを使って監査し、別の数値表で性能を上書きしない。大艦の生成は独立した断片へ分けられる。カタログには実計算した機関・配電・武装・乗員情報を保持し、重複する船体表面メッシュを除いて `catalogOnly:true` を付ける。出撃準備ではこの印を検出し、実際の艦体から構築した完全なプロファイルへ置き換える。随伴艦・敵艦・補給船団にも同じ準備処理を適用する。

```sh
node scripts/update-ship-examples.cjs --keys imperial,venator --patch /tmp/fleet-main.json --audit /tmp/fleet-main-audit.json
node scripts/update-ship-examples.cjs --merge /tmp/fleet-main.json
```

Core SHA256 `7bc4167c…` で実際に構築・保存した27作例の元図面を、[保存図面とチェックサム](../assets/source/ship-example-blueprints/manifest.json) に収録する。このうち26艦を現行コードで再計測し、エグゼクターは現行コンストラクターから新規構築した結果を採用する。図面は時刻とファイル名を含めない決定的なgzipで保存し、アプリはこの資料を読み込まない。保存内容は部品、装備、形状、配線で、統計、戦闘プロファイル、計算キャッシュは含めない。元の反応炉出力とノズル位置は、改装前後を照合するための来歴として記録する。

保存図面の26艦は、区画・砲座を更新してから質量、価格、配電・動力伝達路、蓄電、厳格排熱、実推進と戦闘プロファイルを全て再計算する。監査には各艦の方法を「保存図面の再計測」または「現行コンストラクターでの新規構築」として記録し、元図面のSHA、構築・計算コードのSHA、保存前後の差、比較可能な場合の工学値の差を残す。

```sh
node scripts/replay-ship-examples.cjs --keys imperial,venator --patch /tmp/replayed-fleet.json --audit /tmp/replayed-audit.json
```

既定ではリポジトリ内の圧縮図面を使用する。別の図面群は `--input-blueprints DIR` で指定でき、JSONとgzipを受け付ける。過去の生成断片と監査表を持つ場合は `--baseline-prefix PREFIX` を追加し、同じ入力からの経路・工学値・監査値を比較できる。過去の表がない場合は比較不能と明記し、現在の物理計算による監査を実行する。古い統計やプロファイルを復元して合格扱いにすることはない。

エグゼクターはCore SHA256 `24210165…` で新規構築し、[現行作例の公開図面](../assets/source/current-factory-blueprints/manifest.json) に別途保存する。実部品323個、外装機関13基、実散逸区画7個を備え、反応炉出力 `2e27 W` と元のノズル・外観配置を維持する。配電経路による質量と発熱の変化が支持設備・機関定格・冷却区画の構築にも影響するため、この新規構築結果を最終データへ使用する。元の27図面と旧エグゼクターの再計測結果は、来歴と比較資料として保持する。

```sh
node scripts/update-ship-examples.cjs --keys executor --patch /tmp/fresh-executor.json --audit /tmp/fresh-executor-audit.json --blueprints /tmp/fresh-executor-blueprints
node scripts/replay-ship-examples.cjs --keys executor --input-blueprints assets/source/current-factory-blueprints --patch /tmp/executor-replay.json --audit /tmp/executor-replay-audit.json
```

入力照合では元JSONの差分を残し、既定の有効状態の明示、同じ実区画から求め直した表示直径、既存の傾きの別名などを、実形状・容量が同じという個別の証拠付きで分類する。支持面の計算丸めは、ワールド座標の4 ULP以内でFloat32メッシュが同一、実容積が `1e-12` の比較に収まる場合に別分類する。支持面の座標再基準化は、ワールド座標のFloat64・Float32メッシュと実容積が完全一致する場合に限る。他の入力項目には同じ `1e-12` の照合を適用する。

最終監査は27艦全てで実機関・乗員・蓄電・配電・動力伝達・厳格排熱の確認に成功し、監査条件での失敗は0件。内蔵機関本体96基と一体型機関65基、ノズル174基、配電路171本、動力伝達路109本、蓄電装置4,758個を確認した。各艦で推進を優先した場合の実受電と正の加速を確認し、均衡配電での出力制限は実際の有限電力配分として記録する。

比較元は `c805f05` 時点の [変更前の全27艦の計測](benchmarks/ship-examples-before.json)。途中で取り込んだ新しいレキューザントとミュニフィセントの砲・配置は [原モデルから切り出した武装の仕様](recusant-munificent-guns.md) に従う。計測では、損傷のない冷間状態から30秒間、均衡配電で推進・通常砲・シールドを同時に要求し、実際に割り当てられた電力と推力、発熱を記録する。全要求を同時に満たすことは合格条件にしない。推進のみ、砲撃併用、シールド併用も比較し、有限の電力が各装置で共有されることを確認する。継続排熱の判定は設計プレビューの各運転条件も併用する。

前回の武装・厳格冷却改装（`f5287be`）の [全27艦の計測結果](https://github.com/OKB2025/kuat-shipwright/blob/f5287be/docs/benchmarks/ship-examples-after.json) では、全艦で機関の有効性、機関区画の重なりがないこと、満充電、必要な乗員の収容、改装基準の発電量の保存（マンデイターIIはユーザー指定出力）、8種類の運転条件での電力収支、推進を優先した場合の正の加速を確認した。174基の機関が有効で、通常砲の蓄電装置4,788個は全て満充電。111基の実散逸装置を備え、27艦全てで互換冷却がなく、216通りの配電で電力収支を確認した。機関・収容・電力収支・厳格排熱の失敗は0件。同時出力の制限がある艦は、有限電力の配分結果として記録する。これらは無損傷・冷間状態での検証であり、全要求を無期限に同時達成する保証ではない。

前回改装時の選定テスト43ファイルは324件全て成功し、カタログ・読込サイズの2件も成功した。実画面の記録は [斜面・ファイター](benchmarks/slope-fighter-browser.json)、[可変セル発射装置](benchmarks/ship-launcher-browser.json)、[代表艦](benchmarks/ship-examples-browser.json) を参照。

内蔵機関とノズルを分離したモデルの監査は [作例の計測結果](benchmarks/ship-examples-after.json) に記録する。機関本体の共有、配電の送電・受電・損失熱、ノズルごとの動力伝達、独立した経路損傷を検証し、上記の過去の機関数・テスト件数と区別する。

代表艦のブラウザ照合では、保存図面の冷間再計算と作例の構築直後を区別して記録する。ヴェネターでは同一の公開図面から、Boolean切削後の残存構造材・区画／船体排除量に約12.24 ppmの質量差が出る。保存部品や武装の欠落ではない。保存入力のSHA、部品・装備ID、砲座・充電・機関数を確認し、差がある場合は実際の作例構築をワーカーへ独立に要求して、カタログとの2 ppm以内の一致を検証する。保存後の質量が全大型艦でビット一致するという主張はしない。
