# 表面設備・砲列・エネルギー管理

表面の編集方式は、最新のユーザー指示によって「装甲面」か「機材搭載面」を選び、機材搭載面へ砲列・散熱・センサー・居住区の比率を100%の中で配分する方式へ更新されています。最新の操作・保存形式と旧設定の扱いは [装甲面・機材搭載面の開発報告](surface-equipment-allocation.md) を参照してください。以下の自由なレイヤー重ね合わせ・個数入力・表面v1の記述は、その導入時点の記録です。現在の熱計算は旧保存を含め全設計で厳格運転に統一し、互換冷却と超兵器への散逸能力の自動割当は廃止しています。

この文書は、表面に装甲・機材・砲列・散逸設備を設定する設計モデルと、その共通シミュレーションへの接続を記録します。技術名や数値はゲーム内の仮定です。公式設定の確定した数式、実証されたニュートリノ冷却技術、Discordでの助言を同一の根拠として扱いません。未確定の効率・密度・保護閾値は調整可能な実装値として扱います。

## 採用する境界

表面パッチは編集・保存の単位です。描画用の三角形番号や、カメラ距離、ディテール密度を機能の正本にしません。実際に設置した装置・砲座の位置と数から、容積・質量・要員・電力・熱・被害を集計します。大型の個別砲塔は引き続き配置できます。

面装甲、装置、砲列は別レイヤーです。同じ面を共用する場合も、占有範囲と内部深さを予約します。内部に隠れた区画を透視表示しただけでは、外部への射撃・放熱能力を与えません。砲口・開口・放熱面の露出と、背後の装甲による防御も区別します。

給電・充電・熱輸送・散逸・損傷は既存の部品・兵装・ネットワークを利用します。表面設備やイオン攻撃のために、もう一つの独立した艦内シミュレーションを作る仕様ではありません。

## 設計画面での操作

1. 「編集」タブの「表面」を開き、外面を直接タップするか一覧から選びます。「追加選択」「範囲選択」と一覧の絞り込みも使えます。
2. 装甲、散逸設備・機材、表面砲列、外観の設定を変更し、「選択面へ適用」を押します。複数選択では変更した項目だけを各面へ適用します。基数・ユニット数は面ごとの要求です。
3. 「選択面の搭載と接続」で、要求数と実設置数、面積・深さ・質量・要員・給電・熱の診断を確認します。設置できなかった要求は警告を残します。
4. 「給電・熱輸送を診断」から共通系統を確認します。旧設計も厳格運転で計算し、必要な実設備と熱輸送容量の不足を表示します。

面の分割・結合、設定のコピー・貼り付け、未配置設定の移設も同じ編集欄で行います。変更は既存のUndo/Redoへ含めます。

## 保存と識別

表面設定は設計図の `surfaces` に保持します。ルートの契約は次のとおりです。各フィールドの値域と追加の診断情報は実装側の正規化処理を使います。

```js
surfaces: {
  version: 1,
  mode: 'strict',
  compatAllowed: false, // 旧保存の互換指定も正規化して無効化
  legacyArmor, // 移行前の全艦装甲の基準厚
  patches: [{
    id,
    boundArea, // 対応面が失われた場合に物理量を保持する基準面積
    armor: {material, thickness},
    equipment: {kind, count, depth},
    battery: {weapon, count, spacing, angle, reversed},
    style: {kind, depth, density, seed},
    layout: {u, v}, // 対称コピー時の配置順。各値は1または-1
    powerDomain
  }],
  partitions: [{baseId, leaves: [{id, range: [u0, v0, u1, v1]}]}]
}
```

パッチの親は船体または部品です。パッチIDは親のローカルな面・範囲に対応し、描画三角形の並びを使いません。寸法や姿勢の変更で設定を別の面へ飛ばさず、切削・再メッシュで対応が失われた設定は未配置として診断します。切削で新しく生まれた面へ、古いトレンチや装置を黙って複製しません。

外側の設計保存形式は既存の `starship-yard` v3 を使い、その中の表面データを独立したversion 1として正規化します。表面から生成した通常部品・兵装には、所有パッチと配置セルの情報を持たせます。配置を更新しても、同じセルのIDを維持し、読み込みのたびに同じ設備を追加しません。ユーザーの個別配置兵装は、表面砲列の再生成で削除する対象にしません。

主な公開APIは `surfacePatches`、`surfaceConfig`、`setSurfaceConfig`、`surfaceReport`、`surfacePick`、`surfaceSplit`、`surfaceMerge` です。設定済みパッチは最大512件、1パッチの砲座要求と設備要求はそれぞれ最大256件です。実際の生成先には既存の共通上限である部品1400個・装備2400基も適用します。外面の設定が512件を超える旧設計は、設定を黙って切り捨てず、面の移行を拒否します。熱計算は面設定の有無にかかわらず厳格運転を使用します。これらは機能データの管理上限であり、描画LODや画面上に見えるグリーブルの数から決めません。

手書き・外部生成したversion 1データでも、パッチ記録512件、分割グループ512件、1面の分割64件のいずれかを超える入力は、明示的なエラーで拒否します。読み込み・書き出し・複合部品の配置で余剰データを切り捨てて成功扱いにはしません。複合部品は配置前に検査し、失敗した操作が設計の一部だけを変更しないようにします。

左右対称や複合部品では、親IDだけでなく、面法線、砲口方向、射界、ローカルID、給電・熱輸送リンクを変換します。`layout` のu/vの向きと `battery.reversed` は反射後の物理セル順序・砲口の基準枠を維持する情報で、生成兵装の `frameFlip` / `tilt` と対応します。生成済みの物理部品をコピーしたうえで同じ設備をもう一度生成しないようにします。

## 装甲・設備・砲列の集計

面装甲の厚さと材質から、必要空間と質量を計上します。全艦一括の操作は面への編集操作として扱い、同じ厚さを全艦装甲と面装甲へ重ねて加算しません。非露出の装甲が物理的に残る場合は、非表示になっただけで質量を消しません。

砲列は、砲座基数と1基当たりの砲身数を区別します。既存の同じ武器定義を使い、「8連装1基」と「単装8基」の取り付け・給電・被害を同一視しません。面積だけで搭載数を決めず、細長い面、開口、旋回余地、他の装置、内部深さも配置条件に含めます。

散逸能力は実際の設備規模、接続容量、損傷、運転状態から求めます。通常放熱と架空の高エネルギー散逸は共通ネットワーク上の異なる装置です。装飾密度を増やしただけで、能力・火力・要員が増えることはありません。Sフォイルも既存の装置の露出・運転条件を変える機構として扱います。

厳格運転の散逸設備は、冷えた状態から起動できるように定格の電力枠を予約しますが、実際の消費は共通 `heatSolve` の処理流量に比例します。未使用の予約枠は発熱・放射へ加えません。実消費した電力は設備自身の熱へ送り、主炉の変換損失とは別に記録します。放射シグネチャは実際に処理した熱の帯域から求め、散逸設備を増設しただけで定格相当の輝点を出しません。

`heatStatus.cooling` は待処理の予約量 `reserveJ`、累積予約 `reservedJ`、実入力 `inputJ`、設備自身の熱 `heatJ`、炉の変換損失 `reactorWasteJ`、処理した熱 `handledJ` と直近の電力を分けます。現行の予約は保守的な定格枠で、同じ電力更新内に使わなかった分を他の消費装置へ即座に再配分する最適化は行いません。

設計指標は `S.surface.patches` に、共通の給電経路と熱ネットワークから導出した要求／供給電力、最大／持続射撃、発熱／熱輸送、最大蓄電、割当要員を持ちます。設計画面はその計算結果を表示し、未計算のときは「計算中」とします。上限の蓄電量と戦闘中の残量は別の値です。表面機材は通常の整備区画、散逸設備は通常のhdis／radiator部品、砲列は通常のFITS兵装として集計します。

戦闘HUDは設置数、残存数、稼働数、射撃可能数、砲身総数と兵装蓄電を分けて表示します。砲列ごとの停止原因は破壊、蓄電設備破壊、給電停止、過熱、イオン遮断、要員不足、再充電中です。砲自体が健全でも、接続された蓄電設備の損傷で容量が低下します。失った容量に残っていた蓄電は共通の武装熱へ一度だけ放出します。電力系統の遮断と局所遮断には再起動までの時間を表示し、局所装甲の残存率と、直近のシールド被弾の入射・外部放出・一時蓄積・艦内熱・漏出も表示します。

## エネルギーと防御

エネルギーとして扱うTTの換算は、既存の共通定数 `1 TT = 4.184e21 J` を使います。旧兵器の効果指数を、説明なしに実エネルギーへ置き換えません。物理量としての出力 `E_out`、入力 `E_in`、損失 `E_loss` を区別し、効率 `eta` のモデルでは `E_in = E_out / eta`、`E_loss = E_in - E_out` とします。主炉の発電損失と消費装置の変換損失は異なる収支境界です。

シールドは、入射量を外部への偏向・再放出、一時蓄積の変化、艦内へ移す熱、船体側への漏出へ分けます。自艦が供給した運転電力とは別に記録します。低発熱でイオン攻撃を阻止する場合も、有限の受入量・処理速度・防御余力を消費します。一律の「対シールド3倍」や、阻止した全エネルギーを艦内廃熱へ加えるモデルを新仕様の根拠にしません。

漏出イオンは、命中面や装置に接続された電力ドメインへ作用します。通常は局所の保護遮断と復旧待ちを起こし、十分に大きい、または時間的に集中した過負荷で接続共通網を停止させます。共通網に接続された補助炉も対象です。隔離された独立電源と、共通網へ接続された補助電源を区別します。

保護停止は物理的な破壊と異なり、復電だけで破壊された装置が修復されることはありません。停電中は推力、新規射撃、再充電などを実際の電源状態に従って制限し、慣性速度は維持します。被弾判定に `E / simulationDeltaTime` を使わず、ゲーム内のパルス幅と処理速度を区別します。

広域パルスは、拡大する円盤と距離・投影面積に応じた受領量を維持します。複数艦に初期エネルギーを丸ごと複製せず、命中によって残量を減らします。部分充電と満充電は、実際に充電された量で区別します。艦型を名指しした停止条件は作りません。

エネルギー系の公開APIは `weaponEnergy`、`shieldReceive`、`shieldStatus`、`ionOverload`、`powerStatus`、`powerFactor`、`powerTick` です。`powerStatus` はドメイン単位の給電・放電・イオン遮断と、装置単位の局所遮断を分けて返します。その利用可能電力比は、ドメインの定格に対して、発電設備の物理的健全性と保護遮断を反映します。画面上の「最大射出エネルギー」は、射撃時点までに充電された量とは別の上限値です。

現行の初期係数は、通常兵器の既定効率0.75、超兵器0.88、阻止イオンの艦内熱移送率0.003、通常ビーム0.06です。シールドの一時蓄積上限は防御容量の0.35倍、外部への処理時定数は2秒です。イオン結合率0.35、パルス幅0.25秒、負荷減衰時定数3秒なども、`ENERGY_MODEL`、`SHIELD_MODEL`、`ION_MODEL` にある調整用のゲーム値です。特定兵器や公式設定の確定した効率を示しません。

## 互換性と導入

熱計算は全設計で `strict` を使用します。旧保存の `mode:compat` と互換許可は読み込み時に厳格運転へ正規化し、互換モードへの切替は拒否します。面設定のない設計や旧戦闘プロファイルも、設備内蔵冷却・超兵器への散逸能力の自動割当で不足を補いません。

実際の散逸設備と有限な熱輸送路で廃熱を処理し、運びきれない熱は蓄熱・出力制限・停止へつなげます。旧保存へ設備を無償挿入せず、冷却設備の不足は診断に残します。

厳格化で不足する設備や容積は診断し、不可視・無償の装置を挿入して帳尻を合わせません。個別兵装を勝手に砲列へ変換せず、装甲や冷却の旧値を二重に積みません。初回の表面移行では旧装甲を外面の設定へ写像し、以後の装甲質量は面データから集計します。対応面が失われても基準面積を残し、装甲が見えなくなっただけで質量を消さないようにします。

費用集計は共通の `COST_MODEL` version 8を使います。標準機の参照価格も同じ設計計算から生成し、`node scripts/update-craft-costs.cjs --check` で生成カタログとの整合を検査します。

導入順序は、A: 単位・面ID・既存処理の調査、B: 面と装甲・少数砲列・局所被弾、C: 給電・要員・熱への接続、D: シールドとイオン・停電復旧、E: 外観・LOD・複合部品・移行・性能調整です。高密度の外観より、少数設備での保存・収支・被害の一致を先に確認します。

### 実3D戦闘の機能確認
