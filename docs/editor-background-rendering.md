# 設計計算中の3D操作

設計計算がWorkerで動いていても、形状受信後のマウス移動で主スレッドが機関経路を再計算していた。保存済みインペリアルIの実画面では、この `enginePaths` 呼び出しだけで約4.5秒停止した。

描画・選択に必要な機関経路、指揮区画、砲の充電区画、VLS区画は、Workerの形状パケットから受け取る。性能表示のカタログ値もWorkerで作り、推進の別運転条件は非同期で問い合わせる。表示更新やホバーから同じ物理計算を繰り返さない。

キャッシュ参照の準備はライブ図面と分離して分割する。適用直前に図面、世代、ドラッグ状態、処理番号を再確認し、最新の結果だけをまとめて適用する。途中で置いた砲や移動した部品を古い結果で戻さない。大きなGPU転送は描画グループ間で入力処理へ制御を返し、頂点の境界はWorkerで求めて受け渡す。古い世代のパケットは適用せず、境界情報がない、または不正な場合には従来の頂点走査を使う。

カメラ操作はホバーの遅延判定を取り消す。計算・転送・操作中は影の再描画を待ち、落ち着いたら元の描画設定を復元する。船体や砲のメッシュ、電力・熱・加速度の計算は省略しない。

## 実画面の確認

[検証スクリプト](../scripts/browser-stats-camera.cjs) は、保存済み図面へ通常のキャンバス操作で連装砲を左右に追加し、実Workerの形状・性能計算中にマウス、ホイール、2点タッチを送る。入力は実ブラウザのtrustedイベントとして記録し、各ハンドラーの前後でカメラ値が変化したことを確認する。Workerの待ち時間を延ばしたり、計算結果を注入したりしない。

[修正後の記録](benchmarks/stats-camera-fixed.json) は、比較用に固定した物理Coreと、修正後のApp・Engine・描画器で実行した。最終艦艇の新規構築確認とは別の検査である。速度カタログのコピー変換を加える直前のAppのSHAも記録する。

| 確認項目 | 観測値 |
| --- | ---: |
| 主スレッドの機関経路・推進等の再計算 | 0回 |
| 性能待ち中のマウス・ホイール・タッチによるカメラ変更 | すべて確認 |
| 上記連続入力の往復 | 86 ms |
| カメラ入力ハンドラーの最大実行時間 | 11.9 ms |
| キャッシュの最終適用 | 1.2～1.9 ms |
| 配置後の砲・艦橋等の総数 | 51個を保持 |

[修正前の記録](benchmarks/stats-camera-baseline.json) は4.5秒の経路再計算を検出した。旧入力順序ではソフトウェア描画の待ちにより性能待ち中のズーム確認が欠け、検査全体の状態は `ERROR` のまま保存している。修正後は、描画完了の応答を一つずつ待たず実際の入力と同様に順序を保って入力を送り、各イベント前後の値で確認した。

計測環境はヘッドレスChromiumとSwiftShaderである。修正後も最大約2.1秒のGPU転送待ちと約2.0秒の描画待ちが記録されており、すべてのGPUフレームが止まらないことを保証する結果ではない。実機Safariの描画速度を確認したという意味でもない。
