# 重い艦の計算の無駄の調査（2026-11-25）

ユーザーの依頼：「インペリアル級等重い艦の計算が長く負荷も高いのでどこか無駄な処理がないか、2重3重で行う計算がないかも確認して」

対象：`imperial`（インペリアル級、部品 180・砲 50）。コミット `9893aad`（js/core.js）。全作例の作り直しと並行して測ったので、秒数は実際より長い（比率を見る）。

## 測り方

`path.cjs`：ゲームが作例を開くときの手順（`js/engine.js` の艦隊ジョブ、新しく組む場合）をそのまま 1 段ずつ実行し、時間を測る。`node --cpu-prof` の記録を `stages.py`（段階ごと）と `analyze.py`（関数ごと）で集計した。

## 結果：段階ごとの時間（`imperial-stages.md`、`imperial-by-stage.txt`）

| 段階 | 秒 | 中で走っている重い処理 |
| --- | --- | --- |
| 読み込み（deserialize） | 0.5 | |
| 区画の導出 1 回目 | 11.1 | 占有の一覧 4.0、機関の経路 4.0、構造の切り取り 3.1 |
| 砲の載せ直し | 0.3 | |
| 区画の導出 2 回目 | 7.2 | 占有の一覧 3.6、機関の経路 3.6 |
| 性能計算 | 58.5 | 表面の露出の調査 20.8、装甲の面積 18.0、**区画の導出（3 回目）11.7**、構造材の量 10.4 |
| 性能表 | 0.8 | |
| 性能計算をもう一度（何も変えずに） | 18.5 | 構造材の量 10.0（構造の切り取り 9.9） |
| モデルの生成 | 15.5 | **区画の導出（4 回目）10.3** |

合計 約 112 秒（うちガベージコレクション 約 15 秒）。

## 見つかった重複

1. **区画の導出が 4 回、毎回最初からやり直されている。** 読み込みで 2 回、性能計算の中で 1 回、モデルの生成の中で 1 回。艦は 2 回目以降まったく変わっていないのに、毎回「占有の一覧」「機関の経路」「機関の駆動の網」を計算し直している（各回 3.5〜4 秒ずつ）。4 回で約 39 秒、全体の約 35%。
2. **読み込みの 1 回目の導出は、砲を先に載せれば要らない**（ユーザーの指示「区画より先に砲を乗せる形にして」）。小型艦 6 隻（GR-75、ハンマーヘッド、CR-90、X ウイング、ネビュロン B、アークワイテンズ）で、「砲を載せる → 導出 1 回」と今の「導出 → 載せる → 導出」が、公開状態・保存される設計・性能の全項目で一致することを確かめた（`order.cjs`）。大型艦はまだ確かめていない。
3. **構造材の量（構造物同士の重なりを切り取って量る計算）が、性能計算のたびにやり直されている。** 何も変えずに性能計算をもう一度呼ぶと 18.5 秒かかり、そのうち約 10 秒がこれ。形状が同じなら結果は同じなので、覚えておける。
4. **性能計算は初回 58 秒、2 回目 18 秒。** 差の 40 秒（表面の露出の調査、装甲の面積）は覚えてあって 2 回目は走らない。ここは既に重複していない。
5. 作例の作り直し（`scripts/refresh-examples.cjs`）は、1 隻につき「組み立てて性能計算 → 保存した設計を読み込み直してもう一度性能計算」と全体を 2 回行う。保存した値とゲームが開いたときの値を一致させるための意図的な手順（2026-11-12）。別プロセスではなく同じプロセスで続けて行うので、上の 1・3 が直れば 2 回目は大きく縮む見込み。

## 細かい無駄（関数ごと、`imperial-functions.txt`）

- 砲塔の形の鍵を作る処理（`turretGeometryKey`）が自分だけで 4.5 秒：同じ砲の鍵を繰り返し文字列にしている。
- 搭載機の公開状態を文字列にする処理（`aviationPublicJSON`、`publicCopyOf`）が約 4 秒：モデルの生成の中でキャッシュの鍵として繰り返し作っている。
- 光線と三角形の交差（`rayBVH`）が自分だけで 17.5 秒：区画の導出の「内側か外側か」の判定から呼ばれていて、1 の重複が無くなればその分減る。

## 直す順（案）

| # | 内容 | 見込み | 確かめ方 |
| --- | --- | --- | --- |
| 1 | 読み込みを「砲を載せる → 区画の導出 1 回」にする | −11 秒 | 全作例で公開状態・保存設計・性能が今と一致 |
| 2 | 区画の導出を、艦の状態が前回と同じなら省く | −22 秒 | 同上＋編集（部品の移動・追加）のあとは必ず導出し直すことをテスト |
| 3 | 構造材の量を形状ごとに覚える | −10 秒（2 回目以降の性能計算） | 性能の全項目が一致 |
| 4 | 鍵の文字列化を 1 回にまとめる | −数秒 | 同上 |

どれも結果を変えない変更のはずだが、編集画面（部品を動かしたあとの再計算）と Worker のキャッシュに関わるので、回帰レビューの対象。まだ何も直していない。

## 性能計算（`computeStats`）の中の重複（ユーザー「性能計算自体に重複や無駄な計算はないか」）

`callers.py`／`imperial-computeStats-callers.txt`：性能計算の 1 回目（インペリアル級、約 58 秒のうちプロファイルで 49.7 秒）の中で、重い処理がどの経路から呼ばれているか。

| 重複・無駄 | 秒 | 中身 |
| --- | --- | --- |
| **表面の露出の調査が 3 回走る** | 8.9 + 8.3 + 4.3 | (a) 露出面積の計算、(b) 装甲の面積の計算、(c) 表面の報告。3 回とも面を遮蔽物で切り取る処理（`surfaceExposedTriangles`：7.3 + 6.6 + 3.7 秒）をやり直している |
| **(b) は、開いている引き戸（格納庫の扉）を持つ艦で、扉を閉じた写しを最初から組み直している** | 9.7（区画の導出）＋ 8.3（調査） | `armoredMaterialArea`：扉が開いていると、設計を写して扉を閉じ、区画の導出と露出の調査を全部やり直す。インペリアル級は扉が 2 つ開いているので毎回これに当たる。扉の周り以外の面は開閉で変わらない |
| (c) は、作業用の写しではなく元の艦に対して調査するので、キャッシュが効かない | 4.3 | 調査のキャッシュが「艦の物（オブジェクト）」ごとで、同じ形でも別の物だと調べ直す |
| **構造材の量が毎回やり直される** | 10.4 | `structuralMaterial`：構造物同士の重なりを切り取って量る。結果を覚えていないので、性能計算を呼ぶたびに走る（2 回目の 18.5 秒のうち 10 秒） |
| 遮蔽物の断面の計算が調査ごとに捨てられる | 4.2 + 2.6 | `solidSliceSegments`：遮蔽物ごとの断面のキャッシュ（`sections`）を調査のたびに作り直している |

- 3 回の調査と写しの組み直しを 1 回に寄せられれば、性能計算の 1 回目は 約 58 → 35 秒前後になる見込み（(b) の 18 秒と (c) の 4 秒）。構造材の量を覚えれば、2 回目以降は 18 → 8 秒前後。
- 直し方の案：(1) 露出の調査の結果を「面の形と、その面に届く遮蔽物の形」の内容で覚える（今は物の同一性で覚えているので、写しでは必ず外れる）。こうすれば扉を閉じた写しでも、扉の周り以外は使い回せる。(2) 扉を閉じた写しの区画の導出を、元の艦の導出結果から引き継ぐ。(3) 構造材の量を、構造物の形の内容で覚える。
- 注意：(1) は、Worker が戻した艦の灯りがずれる件（調査の鍵が区画の切り取り後の形を含まない）と同じ場所。一緒に直すのが筋。
