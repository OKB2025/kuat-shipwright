# 公試・艦隊戦の読み込みでタイトルに戻る件（2026-11-27）

ユーザーの報告：「やはりインペリアル級とヴェネター級が公試の読み込み中にタイトルに戻る」
対策の選択：「両方で公試だけでなく艦隊戦も読み込めるように」

前回の調査は [../build-profile-2026-11-25/README.md](../build-profile-2026-11-25/README.md) にある。端末は iPhone の Safari。
タブのメモリが上限を超えるとタブが読み直され、タイトルに戻る。iPhone は無いので、こちらでは再現していない。

## 計測：実際の操作の流れ（ブラウザ、インペリアル級）

`scripts/browser-trial-mem.cjs` の手順：
1. 作例を下書きとして開き、編集画面の計算と表示が終わるまで待つ。
2. 公試を始める。
3. その間、ページと全 Worker の JS ヒープを 0.5 秒ごとに読む（CDP の `Runtime.getHeapUsage`）。

ヘッドレス Chromium、Worker モード。数字は各対象の最大値（MB）で、合計はある時点の合計の最大値。

| 版 | 編集画面を開く | 公試の読み込み |
| --- | --- | --- |
| 変更前（origin/main 790afd4a） | 148 s、合計 **1,536**（ページ 251、Worker 947、**背景の準備の Worker 710**） | 64 s、合計 1,205（ページ 255、Worker 760、**背景の準備の Worker 370**） |
| 背景の準備を待たせる（a12149f0） | 131 s、合計 1,108（ページ 251、Worker 929） | 44 s、合計 1,299（ページ 272、Worker 1,076） |
| ＋公試で艦の写しを作らない（cf769541） | 132 s、合計 1,167（ページ 251、Worker 988） | 34 s、合計 **1,028**（ページ 270、Worker 804） |

記録：`browser-base-imperial.json`、`browser-cand1-imperial.json`、`browser-cand2-imperial.json`。サンプルは 1 秒ごとに間引いている。

ヒープの使用量には、まだ回収されていないごみも含まれる。このため、同じ版でも数十〜百 MB 程度は揺れる。

## 見つかった原因

1. **背景の準備（`KSPreload`）が、重い計算と並んで動いていた。**
   - 背景の準備は、作例と保存した設計の戦闘用データを、別の Worker で前もって作る仕組み。
   - 待つ条件（`busy`）に、次の 2 つが入っていなかった。
     - 公試の読み込み中（`trial.busy`）。公試のボタンを押すと 2 秒止まるが、読み込みの途中で再開していた。
     - 編集画面の計算中（`eng.statsGen < eng.gen` など）。
   - その結果、インペリアル級を開くと、編集画面の Worker（947 MB）と同時に、別の Worker が別の作例を作っていた（710 MB）。
2. **公試の Worker が、編集中の艦をもう 1 隻作り直していた。**
   - 編集中の設計の公試では、`packCaches` から `rehydrate` で写しを作り、それを公試の間ずっと持っていた（`trialHold`）。
   - 編集画面の艦と合わせて、艦が 2 隻分になっていた。

## 変更

- `js/app.js` の `preloadBusy`：背景の準備は、公試の読み込み中と、編集画面の計算・モデルの作成中にも待つ。
- `js/engine.js` の `handleFleet`（src `editor`）：公試は編集画面の艦をそのまま使う。
  - 艦を書き換える処理は無い。扉が動く艦のモデルは、`fleetGeometry` が描画用の写しで作る。
  - 公試の読み込み中、編集画面は操作できない。
- `js/engine.js` の `fail`：Worker が落ちたら、新しい Worker で再開する。
  - 以前は、同じ計算をページ側（inline）でやり直していた。重い艦では、落ちた直後にページ側でも同じ山を作ることになっていた。
  - 再開が 2 回失敗したときだけ、以前どおり inline にする。
  - 再開中に失敗がもう一度届いても、Worker を 2 本は起こさない。
  - 再開した Worker は設計を持たない。このためページは `restart` を受けて、設計全体を送り直す（回帰レビュー、2026-11-28）。
  - テスト：`tests/engine-worker-restart.cjs`。
- **作例の計算済みの数字（`data/examples/<key>/prepared.json.gz`）**：表面の区画を持つ作例（29 隻）に、性能表の全体と表示用の数字を同梱する。
  - `scripts/refresh-examples.cjs` が、Worker と同じ手順で作る（設計の読み込み → `remount` → 区画の導出 → `computeStats` → `fleetProfile` → `statsOut`）。
  - 艦隊戦・観閲式など、作例を名前で読み込むときは、Worker が性能計算をせずにこれを使う。
  - 艦隊戦は作例を `lite` で要求する。最初の版は、`lite` の要求で計算済みの数字を使っていなかった（回帰レビュー、2026-11-28）。表面の区画を持つ艦は、もともと `lite` にならない。そのため、条件から外した。
  - 使うのは、モデルの鍵・表示の作り方の鍵・設計のハッシュが今のものと一致するときだけ。
  - 艦隊戦の作例の読み込みの時間とメモリの、ほとんどを占めていた計算が無くなる。
  - 29 隻分の合計は 111 MB（gzip）。最大はマンデイター II 級とミュニフィセント級で、各 16 MB 台。
  - ブラウザが取りに行くのは、Worker が作例を名前で読むときだけ。背景の準備が作例を順に作るときも、ここに含まれる。

## 計算済みの数字の確認

`prepared-vs-computed.txt`（`scripts/compare.cjs`）は、Worker が計算した性能表・表示用の数字と、同梱する数字を、全項目で比べた。

- インペリアル級・ヴェネター級・CR90 とも、数値の相対差は最大 0、数値以外の差は 0。
- 数えている「差」は、ゼロの符号だけ（JSON は -0 を 0 として書く）。
- 最初の版は、作例の性能表の行と同じ手順（区画の導出を 2 回）で作っていた。この版では、インペリアル級の 1 区画で露出の割合が 0.081 対 0.071 とずれた。このため、Worker と同じ手順に改めた。

## 作例を名前で読むときの Worker の処理（node、計算済みの数字あり）

`scripts/workerjob.cjs` は、Worker の `fleet` の処理を node で動かし、時間と常駐メモリの山を測る。この処理は公試・艦隊戦が作例を読むときと同じもの。

| 艦 | 変更前（`worker-job-before.txt`） | 変更後 20fdd635（`worker-job-prepared.txt`） |
| --- | --- | --- |
| インペリアル級 | 104 s、山 1,094 MB、性能は計算 | 34 s、山 708 MB、性能は計算済みの数字 |
| ヴェネター級 | 85.5 s、山 1,102 MB、性能は計算 | 35 s、山 791 MB、性能は計算済みの数字 |

- 変更後の計測は、全テストを並走させた状態で行った。このため時間は長めに出ている。
- 返す性能表・表示用の数字の大きさは、変更前と同じ。
- 数字の中身の一致は、上の「計算済みの数字の確認」を参照。
