# 面単位の集約機材

機材面の設定を面全体で扱い、生成した機器を設計の個別パーツ一覧へ追加する方式を変更します。散熱・センサー・居住区の3種類で100%を配分し、砲列は兵器と基数を指定する操作を維持します。面の機能と比率から連続した機材の外観を作ります。

[構造体に組み込む機材面](surface-integrated-equipment.md) は、表面v3と個別に生成するパーツを使った段階の報告です。その画像や435項目のブラウザ確認を、今回の集約方式の検証件数へ含めません。

## 保存するデータと計算用のデータ

設計の `ship.parts` と `ship.fits` には、手配置した構造物・機器・兵装を残します。面から生成する設備と砲列は、面設定に属する `aggregate` へまとめます。機材を選んで移動・編集する操作は作らず、面の比率・深さ・兵器・砲座基数を編集します。

外側の設計保存はv3を維持し、内部の `surfaces.version` は4へ更新します。配分、自動設定、対称選択、生成シード等の設定に、面が所有するコンパクトな集約データを加えます。

```js
surfaces: {
  version: 4,
  patches: [{
    id,
    allocation: {cooling, sensors, habitation},
    battery: {weapon, count, spacing, angle, reversed},
    aggregate: {
      version: 1,
      signature,
      cells, // 面が所有する内部の容積・位置・機能等の数値行
      guns   // 明示した砲座の位置・向き等の数値行
    }
  }]
}
```

`cells` は配置予約と互換性のための内部データです。保存するパーツオブジェクトや、個別編集できる機材ではありません。位置、寸法、機能、稼働／未配置、旧ID、容積、費用等を保持します。表示する箱や配管の個数とは別です。砲座も面に所有され、元の兵器定義、砲身数、基数の区別を維持します。

`surfaceSync` が、面の設定と形状に応じて集約データを作ります。物理配置の署名には、塗装・装飾設定・Workerの描画用形状の到着状態を含めません。通常の再読込や照会で配置し直さず、物理設定が変わった場合に配置を更新します。

`surfaceDerivedFits` は砲列の計算・描画に必要な兵装情報を派生させ、`surfaceRenderFaces` は面単位の簡潔な外観用の報告を返します。`surfaceRenderKey` は、描画用形状・実際の集約データ・外観設定の更新を描画へ伝えます。これらの派生結果を、設計の個別パーツとして保存し直しません。

`surfaceRenderClone` は、閉じたスライド扉等の描画用コピーにも、元の面の集約データを引き継ぎます。表示用の形を作るだけで、設備の配置を計算し直したり、元の設計や扉の開き具合を変更したりしません。

## 共通の性能・戦闘処理への接続

`surfaceWorkingShip` が共通処理へ渡す計算用の設計を作り、WeakMapで再利用します。非兵装設備は1面につき最大3つの稼働アダプターと3つの未配置アダプターへまとめ、砲列は明示した砲座の情報を渡します。この計算用データは設計本体と分けます。未配置の物理在庫は質量・費用を保持しますが、稼働能力を加えません。

Workerの `packCaches`・`conv` は、計算用設計へ戻る参照を通常の船体参照へ正規化します。性能計算後の表示更新で、一時的なアダプター群までキャッシュ転送に入り込む経路を除きます。

Workerの性能計算結果には、同じ共通処理で作った艦のプロファイルも含めます。表示側のEngineクライアントは設計の世代ごとに保持し、`trialProfile` が再利用します。`setShip` で設計を置き換えると破棄します。古い応答形式の代替表示でも設計形状を渡さず、公試カードを描くために画面側で居住・容積・部位を再計算する経路を除きます。

|共通処理|集約設備の扱い|
|---|---|
|質量・容積・費用|予約した区画の容積・面積・費用を集計します。大きな代表箱の容積に置き換えません。|
|センサー・管制|元の区画ごとの帯域別開口・管制能力を集計して渡し、まとめた容積へ非線形な式を1回適用することによる能力差を避けます。|
|給電・熱輸送・散逸|既存の電力・熱ネットワークへ接続します。面設備だけの別の艦内シミュレーションは追加しません。|
|居住・要員|既存の居住容積と要員需要の処理を使います。機材の見た目から乗員や居住能力を作りません。|
|兵装・戦闘プロファイル|既存の兵器定義・充電・射界・発射位置を使います。手配置砲塔の処理を維持します。|

`partVolume`、`partArea`、`partBuildCost` 等は、計算用アダプターの予約量を使います。`computeStats`、`heatNetwork`、`sensorSuite`、`habitationSpace`、`fleetModules`、`fleetProfile` は同じ計算用データへ接続します。兵装の蓄電設備、給電経路、Sフォイルの所属判定も同じ計算用データを使います。旧区画の内部接続は、対応する面・機能の接続先へまとめ、並列接続の容量を引き継ぎます。

設計画面は、設備の個数ではなく、各機能の予約面積・占有面積・未使用面積、設備容積を表示します。兵装の砲座基数と砲身総数は引き続き表示します。要員・給電は面の共通集計から表示し、保存していない個別兵装を設計の配列から探し直しません。

## 旧v3からの移行

面が生成した旧パーツ・兵装は、既存の配置を再計算せず、所有する面の集約データへまとめます。手で置いたパーツ・砲塔はそのまま残します。稼働中の設備と未配置の設備を分け、未配置でも所有していた寸法・容積・費用等を引き継ぎます。読み込み時は数値行を検証し、容積を区画の寸法で制限し、費用は共通の部品定義から求めます。

v2の4種類の配分を保持する `legacyAllocation` も引き継ぎます。機材の比率か砲座基数を編集して適用するまで、その互換状態を扱う方針は維持します。対称コピーは集約内のIDも新しくし、内部接続を対応先へ移します。移行と通常の再読込、面の設定変更、コピー・対称の結果は、検証で分けて確認します。

面を分割した場合、設置済みの砲座は位置に対応する子面へ移し、IDと座標を保ちます。未設置の要求分だけを面積に応じて分けます。結合時は要求・設置済みの合計を保ち、分割・結合だけで兵装や所有設備を複製しません。

装甲と機材を重ねた旧式の `functionMode: 'legacy'` は、装甲外面に最大3種類の共通機能表示を残します。個別パーツは再生成しません。現行の機材面は引き続き構造体の内側へ収めた連続外観を使います。

## 外観と読み込み負荷

`surfaceRenderFaces` が返す分類ごとの占有面積・使用可能な範囲・機能IDから、面全体の連続した機材を生成します。分類を示す作動面の配置枠は、受け入れた筐体に合わせて1面96か所以下とし、その枠からグリル、センサー、窓等を描きます。配置予約の行ごとに一つずつ描く方式をやめ、外観上の個数を散熱能力や要員数に変換しません。

筐体、下地、縁の内壁、埋込砲口の枠は、親の船体・構造物の塗装色を引き継ぎます。同じ色相の明暗で凹凸を表し、機能面や窓の表示は残します。

描画計画は4件、生成メッシュは2件を上限として再利用します。`surfaceRenderKey` に加えて実際の集約データ、塗装、画質等で更新を判定し、カメラ位置はキーへ含めません。面の形・配分・塗装を変えた場合は更新し、視点だけの変更では同じ形を使います。

装甲線はUV方向に加え、シェーダーの模様の描き方を修正しました。従来の細かい板模様が1画素より小さくなると、余分な斜めの網目として見えていました。影、編集線、重複面、JPEG圧縮を除いた同じカメラの確認でも残り、UVを艦座標へ直接置き換えるだけでは解消しませんでした。

新しいシェーダーは、艦のX/Zに沿う主な継ぎ目を1画素が覆う範囲で平均して描き、画素より細かくなった板模様だけを弱めます。近景で判別できる細部と主な継ぎ目は保ちます。微分機能を利用できる環境ではその画素範囲を使い、利用できない環境向けの推定計算も用意します。参照モデル、手配置砲、太陽光パネルの模様は対象外です。

個別に保存・管理する設備を減らすことと、画面へ出す箱・配管を減らすことは別の変更です。読み込み負荷は、設計の取得、Workerの計算、描画の完了を分け、同じ入力と画質で比較します。初回の配置計算や大きな艦の描画がすべて一定時間で終わるとは見なしません。

## 検証と計測

Coreの集約・互換・分割結合・コピー・対称・局所被害、UI、実Worker、既存部品・兵装、描画の関連試験群は、それぞれ成功しました。実行群は重なるため、一意の総件数として合算しません。スライド扉を持つ描画用モデルを2回生成しても、追加の配置計算は0回で、元の集約データ・扉の開度・派生兵装の姿勢が変わらないことも確認しました。

最終ソースのブラウザ機能確認は60項目・11群が成功しました。360行の予約・費用、実際の砲座変更とUndo、外観変更、公開保存の再読込、390px幅のタッチ模擬操作を確認しています。公試カードはWorkerのプロファイルを再利用し、表示側の `C.fleetProfile` 呼び出しは0回でした。前後各3回の計測と最終機能確認は、それぞれソースハッシュが安定しています。通常の実行状態で撮影した [装甲の斜視](images/surface-aggregate-armor-angle.jpg)・[上面](images/surface-aggregate-armor-top.jpg)・[親の塗装を継承する機材面](images/surface-aggregate-painted-host.jpg)・[近景](images/surface-aggregate-machinery-detail.jpg) は検証用構造物の画像です。アプリ・コンソール・WebGLエラーはなく、ブラウザは終了しています。

価格カタログ12件の確認も成功し、コストモデル9を維持しています。表面v4用の署名を除き、金額・資源等の数値は `e1cf2af` と同じです。変更したJavaScript5ファイルの構文と差分確認も成功しました。静的確認、Node試験、実ブラウザの操作・計測を区別しており、物理端末、航行を続ける公試、一連の艦隊戦を検証した報告ではありません。

## 近似と制約

内部の予約位置・形状は保持しますが、非兵装設備の運用状態と損傷は、計算用にまとめた面・機能の単位を使います。電力・熱の接続には、その群の容積で重み付けした代表位置を使います。局所命中の範囲と、故障・能力低下を保持する単位を区別し、小箱やグリルごとの独立したHP・配線・AIは作りません。

内部の占有・照会では、予約形状や限られた代表点を使います。装甲を全体として立体化し、各機材へ通路を開けるCSG実装ではありません。描画品質やカメラ距離から、装備量・費用・能力を増減させません。
