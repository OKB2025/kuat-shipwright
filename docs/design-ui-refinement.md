# 設計操作の整理と配置検証の改善

2026-11-08。基準は main `a4d3251141ad7f42caaa6248a6e58c8691ed9f21`。
PR #70後の高さ編集、配置・編集の操作、一括削除、航空ハッチ、迎撃の変更は
[設計操作・配置・迎撃の修正](design-height-placement-fixes.md)を参照する。
[v1.2の実装状況](design-placement-v1.2-status.md)への追補であり、以下の追加指示を優先する。
骨組み重量・強度寄与・縦強度による加速／推進入力制限と、その係数は維持する。
追加指示「基本設置そのものができれば良く計算はバックグランドで後回し」に従い、
タップ配置は軽い入力検証で先に受け付け、厳密計算の完了を待たせない。

## 操作

- 下部は外装／内装、新規配置、設置一覧、性能。旧「詳細」と旧タブを表示しない。
  系統・配電・機関の操作は、その部品の配置・編集に含める。
- 新規配置は全画面のカタログと設定。左右・上下対称を設定し、「設置」で3Dへ戻る。
  面へのタップごとに安定ID付きの元入力をすぐ配置する。手動の「確定」は不要。
  同じ部品・設定を保持して連続配置し、切り取り・干渉・性能はWorkerで後から計算する。
- 一回のタップを一回のUndoとし、その配置の対称相手は同じ操作に含める。
  形状計算の完了でUndoを増やさない。失敗した部品は理由と編集元を保持して修正できる。
  移動・削除・Undo・別設計への切替後に、古い結果で入力を戻したり部品を復活させたりしない。
- 通常の部品タップは小さい情報窓。明示した「編集」で小さい編集窓を開く。
  情報表示だけで設計・履歴を変更しない。外装と内装の選択・編集範囲を分ける。
- カタログ・設定の選択や再描画でスクロール位置を失わせない。
- 「公試」は上部の「メニュー」「設計図」と同じ列へ移す。
  重複するカタログ最大性能カードを除き、共通Coreから得た性能と点検を表示する。
- 点検は右側の諸元の下へ移す。件数を開くと実際の問題と対象を表示し、
  該当部品の情報・編集へ移動できる。性能画面と重複させない。
- 設計図画面の重複ライセンス表示は除く。タイトルの使用素材とライセンスは
  元の8段落・94リンクを保持する。

## 実形状と接触

新しい水平・垂直配置は `placement.contactFit = 'cut'` と要求位置を保存する。
親へ重なった子の体積を切り取り、親・指定姿勢・外側の意匠を保持する。
親の最高点へ部品全体を持ち上げたり、接触を装う面や埋め草を足したりしない。
元形状・有効形状・有効容積は区別し、表示・接触・質量は同じ有効形状を使う。
旧配置にこの方式を推測して適用しない。

実艦の所有船体 #178（実メッシュ10,891三角形）では、接触側の分割に重複・微小片が
生じて閉領域の検証に失敗する条件を修正した。有限な接触領域を順番に分割し、
近接した辺の交点を外挿しない。子の局所的な分割誤差と親全体の接触許容差を分け、
体積を持たない折返しを除く。親の作例を作り直したり、閉領域・最小厚みの検証を省略したりしない。
`native-structure-contact-cut.cjs` は実船体上のX700・X1100で、閉じた子・実接触・
要求位置と上面の保持・親の無変更・保存後の再生成を確認する。

高さは接触面を固定して変更する。上下鏡映では下へ伸びる。
位置は元の要求形状を基に連続した接触範囲で制限する。
さらに埋め込むことはできるが、浮く位置や開口を飛び越えた先へ移さない。
移動限界の内側に残す数値余裕は要求形状の軸幅の `1e-4`。
幅20mでは2mmで、点・辺接触を面接触として通すための許容差ではない。
親自身の移動・形状更新は、子の手動移動制限とは区別して依存順に再評価する。

兵装の小プレビューは、設置に使う砲・支持台の設定を共用する。
支持台の形、寸法、方向を省略した別の仮モデルへ置き換えない。

実UIで使う台形の要求形状でも、下側の斜め壁を親との重なりで切除する。
その壁を保護する上面と取り違えない。上面を貫く親の突起は引き続き最小厚み違反とする。
大きな切断面で同一平面上の辺を自己交差と誤認していた判定は、
辺の長さに応じた浮動小数点の丸め誤差で補正する。物理的な接触許容差は変更しない。

## 見えていない描画

既存の船体・構造物の背面カリングと深度テスト、埋没面を除く露出面の集計は保持する。
追加で、アップロード済みメッシュの実際の描画境界をカメラへ投影し、
画面外・カメラの後ろへ完全に出たメッシュの描画命令を省く。
回転・中心・拡縮・移動は実際の頂点シェーダーと同じ順に適用する。
画面境界を横切る形やカメラを包む形、境界が不明な形は描画を維持する。
開いたノズル・薄い兵装面・透視表示を一律に片面表示へ変更しない。
選択・接触・物理・保存に必要な形状は削除しない。
これは全艦の遮蔽関係を調べる新しい計算ではなく、描画命令の保守的な省略である。

## 部品分類

- 広域・局所シールド発生器は内装。
- 「防御・船体維持」は「機能区画」とし、着陸脚とリパルサーリフトをまとめた
  「着陸設備」を置く。
- 超兵器は兵装。兵装は種別と実際の出力による小タブで絞り込む。
- 航法コンピューターと、射撃管制・照準をまとめた「射撃指揮装置」は指揮設備。
- 旧操縦席のID・座席数・宇宙服設定を保持して、外装の「キャノピー」とする。
  形状を変更した場合はCoreの実形状とWebGL表示・判定・保存を一致させる。
  別の射手座席は要求しない。
- 独立したVLS弾庫は新規配置から除く。発射管の既存弾薬・予約区画・戦闘機能と、
  旧図面の機器IDは保持する。

旧図面の着陸脚・照準コンピューターなどは読込・編集・保存できる。
統合した新規部品を選ぶ経路と、旧図面の互換性を分け、既存作例を自動で再設計しない。

## 切り取り航空区画とハッチ

ハッチ追加時に、切り取り済み航空区画を未切断の要求形状へ戻していた不具合を修正した。
ハッチを持つ区画の再計算を一律に拒否して有効形状を破棄する処理を改め、
解決した有効形状と実際のハッチ接触を検査する。再計算に失敗しても、
直前の有効形状を未切断の大きな区画へ置き換えない。

内部の利用可能領域には、ハッチ穴を区画から二度切り取らない母体の包絡を使用する。
実際の船体形状・元からある切削は保ち、描画する船体とハッチの開口は元の物理処理を使う。
ラベル・航空用途・ハッチ設定だけを変えた場合も、表示・選択用の切り取り済みキャッシュを保持する。
位置・寸法・配置方式・母体を変更した場合は適切に無効化し、Workerの新しい有効形状へ更新する。

`clipped-hangar-hatch.cjs` と `hangar-hatch-editing-ui.cjs` は、要求4,000／有効3,200m³の
実区画でハッチ追加・開閉・透過・削除・スライド・保存復元・描画と選択を確認する。
元からある切削で3,000m³となる場合はその切削を残す。
母体を広げて本当に全体が収まった場合の4,000m³への更新と、旧自動切り取り・所有船体も対象にする。

## 配置検証

配置要求の面解決は選択した親と安定面へ絞る。必要な祖先と、厳密な干渉に使う
他の配置済み形状を復元し、全艦の露出面を毎回列挙しない。
変更されていない元設計の形状キャッシュは再利用する。
厳密配置APIとトレンチ設定用の配置Workerは、既存の検証済みソースから起動し、
長い性能計算の待ち列から分離する。通常のタップ配置はその完了を待たず、
既存の設計更新Workerで形状・性能を後処理する。
取消・設計ID・親子の世代・操作IDの照合とinlineフォールバックは維持する。

全艦の面調査が終わる前でも、Workerが先に返す実形状のキャッシュを使って面をタップできる。
現在の入力・形状コンテキストを確認し、選んだ親の安定した面IDは配置Workerで解決する。
明示した面IDが失われた場合に、別の面へ自動で置き換えるための経路ではない。
入力スレッドで船体を再生成したり、境界箱を最終的な面ヒットとして使ったりしない。
手前の形状を確認できない場合は待機し、背後の構造物を選ばない。
配置直後の子も、現在の元入力から実際に主画面へアップロードした要求形状を使って
追加元にできる。この場合は暫定形状であることを保持し、親から依存順に厳密計算する。
計算済み形状を使う場合も、現在の元入力・親・形状コンテキストの一致を確認する。

軽量な表示が出た段階で、形状・性能の計算まで完了したとは表示しない。
計算待ち・計算失敗を区別し、不成立は対象の部品に理由を表示する。
計算待ちの元入力は図面として保存・再読込できる。未検証の新規部品がある設計から、
稼働能力を保証した戦闘用プロフィールや完成艦キャッシュを作らない。

## 検証記録

画面の比較条件は [変更前](benchmarks/compact-design-ui-before.json)。
844×390の旧編集窓では、固定アクションの下に残る操作領域が約53pxだった。
画像と測定は認証済みの既存ユーザー図面から8部品を保持したUI試験であり、
残り77部品と51 fittingsを除いている。完成艦全体の性能を表す数値ではない。

[変更後の5画面試験](benchmarks/compact-design-ui-after.json)は、
844×390、896×414、1280×588、390×844、1440×1000ですべて成功した。
実タップによる情報表示・小窓編集・数値入力・取消、全画面配置メニューと対称設定、
カメラ保持、設置一覧・性能、外装／内装の選択範囲、諸元と点検への到達を確認した。
844×390で固定アクションの下に残る編集領域は167px、適用・取消ボタンは高さ28pxとなった。

[機能試験](benchmarks/compact-design-ui-functional.json)では、分類・兵装絞り込み、
キャノピーと支持台の有限な実メッシュ、縦横のスクロール保持、点検からの移動を確認した。
実船体への2回のタップは136msで入力を保持し、詳細計算は約14.45秒後に確定した。
両方の子で閉じた形状・実接触を検査し、それぞれ1回のUndoで取り消せることを確認した。
これらの時間は共有環境の機能観測であり、端末の速度保証ではない。
いずれも実Workerを使い、実行前後のソースは一致し、ページエラーは0件だった。

配置時間の比較は `scripts/benchmark-placement-validation.cjs` で取得する。
実Mandator IIの保存図面と同じ面へ同じ兵装を要求し、完成艦条件では318部品と
534 fittingsを残す。変更前の時間切れは完了時間の下限として報告し、
Node処理時間・実ブラウザ操作時間・描画性能を混同しない。

実Safari・実iPhoneは未検証。Chromiumのタッチ入力とSwiftShaderによる
画面確認を、実機での速度・メモリ・Safari互換の検収として扱わない。

### Node試験と配置時間

[検証JSON](benchmarks/compact-design-validation.json)に実行した57ファイルのコマンド、
ソースと試験のSHA-256、結果を記録した。**521件成功、失敗0、skip0**。
実行前後のソースと試験は一致している。対象は編集と連続配置、Workerの世代・取消、
実接触と切除、保存・コピー・鏡映、内装、支持台の実メッシュ、分類とキャノピー、
旧シールド追従、右側点検、既存物理・トレンチの関連回帰であり、全リポジトリ試験ではない。
別途 `node --test --test-reporter=tap tests/craft-systems-localization.cjs` の6件が成功した。
追加ラベル・Coreの部品名と説明・新エラー26項目も実I18N resolverで英訳されることを確認した。

旧試験の手動確定、後続タップによる前候補の取消、外装シールドという前提は、
今回の指示に合わせて更新した。親と安定面・実際のCoreと描画・世代・取消・履歴の検証は維持する。
独立レビューで見つけたスクロール対象、斜面キャノピー、旧シールド追従、
コピー後の支持台設定、計算前ノズルの選択枠例外は修正し、回帰条件を追加した。

[配置時間JSON](benchmarks/placement-validation-latency.json)の固定ソースで得た結果：

|条件|main `a4d3251`|変更後|
|---|---|---|
|実Mandatorの選択親のみ|15秒内に2回完了、約1.91秒・4.99秒。4回の比較は時間切れ|4回成功、約0.21〜1.47秒|
|全318部品・534 fittings|15秒のプロセス予算内に最初の検証が未完了|4回成功、約0.32〜0.81秒|

同じ面・兵装・保存図面を用い、全艦条件では元の兵装1基だけを取り外して再要求した。
旧版の15秒は起動を含む時間切れで、正確な完了時間や倍率は求めていない。
変更後はWorkerの処理経路を通すNode VM内の厳密検証時間である。
通常のタップ操作はこのAPIを待たずに配置するため、この表をタップ時間の改善値として使わない。
厳密検証は取付設定・面IDの有無・計算負荷によって所要時間が異なる。
この表を画面操作時間や完了保証値として使わない。
同じ共有ホストで機能試験も実行しており、他処理との個別の重なりは計測していない。

互換API用の配置専用Workerは独立したCoreランタイムとキャッシュを持つため、
使う場合はメモリを追加で使用する。通常のタップ配置では起動しない。
JSONのNode RSS／heapは独立したテストプロセス全体の観測値で、
ブラウザWorkerの増分・GPUメモリ・端末全体のピークへ換算しない。

### 全艦の即時配置

[実ブラウザの記録](benchmarks/full-mandator-placement-latency.json)では、
318部品・534兵装を保持したMandatorで、全艦の面調査が終わる前に実形状へタップした。
安定IDの追加まで791ms、実際の有限な描画バッファを使う最初の描画まで1.357秒だった。
通常配置の厳密API要求・追加Worker起動は0。計算中のUndo/Redoも同じIDで成功した。
主画面のJS heapは49.98MBから74.63MBとなったが、Worker・GPU・プロセス全体は含まない。
共有環境のSwiftShaderで他の試験と並行した観測値で、実機の応答時間やFPS保証ではない。
別の10秒の観測後も詳細計算は保留中だったため、全艦の形状・性能の完成は宣言しない。

別に確認した `propulsion-model.cjs` の
`integrated nozzle edits retain body dimensions and rating while keeping the body attached` は、
変更前mainと変更後の双方で失敗する既存条件（12件中11成功）。
今回この既存失敗を解消したとは扱わない。

描画側の追加調査では `armor-skin-renderer.cjs`, `screenshot-renderer.cjs`,
`runtime-foils-renderer.cjs`, `surface-renderer.cjs` の34件中22成功・12失敗だった。
別ディレクトリへ取り出した基準mainの全ランタイムでも、同じ12件が失敗した。
最終ソースで再実行して失敗項目が一致することを確認したが、合格とは扱わない。
コマンド・各項目・ログのSHA-256は [既存失敗の記録](benchmarks/compact-design-known-failures.json)に分けた。
